부하 테스트 툴킷 구축 계획

SuperSocketLite의 성능·안정성 변화를 재현 가능한 수치로 판정하기 위한 더미 클라이언트, 시나리오, 측정, 분석 도구의 구축 계획이다. 다음 세션의 구현 착수 문서로 쓴다.

대상 저장소 SuperSocketLite2 · 작성일 2026-08-13 · 단계 1~4 구현

진행 상황 — 단계 1~4 구현

단계 1에서 측정 정확도 문제 4건을 고쳤다. 실행 전체 p99가 남고, 분위수가 표본 추출 비율에 영향받지 않으며, 정상 구간만 집계된다 (3장).

단계 2에서 부하 생성을 열린 루프로 바꿨다. 목표 달성률이 96.8%에서 99.9%로 올랐고, 응답이 늦어져도 부하량이 유지된다(닫힌 루프 84.8% 대 열린 루프 100.0%) (4장).

그 과정에서 세션 수 계측 버그도 찾아 고쳤다. 접속·종료 이벤트 순서가 뒤바뀌면 활성 세션 수가 영구히 어긋나 없는 누수를 있다고 판정하고 있었다(4.4절).

단계 3에서 다룰 수 있는 상황을 넓혔다. 받아 줄 서버가 없어 실행할 수 없던 UDP·text-line 시나리오가 실제로 돌고, 순간 폭주·비정상 종료(RST)·대용량 페이로드 시나리오가 추가됐다 (5장). 서버 계측 확장(C5)은 라이브러리 API 변경이 필요해 보류했다.

단계 4에서 실행부터 판정까지 자동화했다. 명령 하나로 서버 기동·부하·리포트가 끝나고, 기준 실행과 비교해 회귀를 판정하며 불합격이면 종료 코드로 알린다(6장).

자체 테스트 80건 통과, 빌드 경고 0개. 남은 항목은 선언적 시나리오 정의(B2), 서버 장애 주입(B4), 계측 오버헤드 검증(C6), 그리고 판단이 필요한 서버 계측 확장(C5)이다.

2.1 부하량이 목표에 못 미친다 — 그리고 구조적으로 더 미달할 수 있다

목표 초당 500요청에 대해 정상 구간 평균 484.4요청만 발생했다. 원인은 두 가지이고, 성격이 다르므로 구분해야 한다.

  1. 타이머 해상도로 인한 상시 미달 (관측된 3.1%) — 현재 페이싱은 Task.Delay(think time)이다 (LoadScenario.NextThinkTime). Windows 기본 타이머 해상도는 약 15.6ms라 200ms 지연 요청이 실제로는 더 길어지고, 그 오차가 사이클마다 누적된다.
  2. 닫힌 루프 구조로 인한 잠재 미달 (부하가 커질수록 확대) — ClientActor.RunTcpLoopAsync는 요청 하나를 보내고 응답을 받은 뒤에 다음 지연을 시작한다. 즉 사이클 시간 = 지연 + RTT다. 서버가 느려지면 부하 발생량도 함께 줄어들어, 서버가 힘들어질수록 부하가 약해진다. 이번 실행은 RTT가 0.3ms 수준이라 영향이 미미했지만, 고부하에서 RTT가 커지면 이 항이 지배적이 되고 지연 시간이 실제보다 좋게 측정된다.
왜 중요한가

성능 개선의 before/after를 비교할 때, 느려진 쪽은 부하도 함께 줄어 "지연은 비슷한데 처리량만 낮은" 모습으로 나타난다. 회귀를 놓치거나 크기를 과소평가하게 된다.

2.2 실행 전체의 p99가 어디에도 남지 않는다

ClientRuntime의 샘플러는 1초마다 Snapshot(resetLatency: true)로 히스토그램을 비운다. 그래서 client_samples.csv의 분위수는 모두 "직전 1초 안의 p99"다. 이번 실행에서 그 값은 529µs에서 6,321µs까지 흔들렸다. 초당 약 500샘플에서 p99는 상위 5개 값이라 통계적으로 불안정할 수밖에 없다.

그런데 client_summary.csv에는 클라이언트 수, 실행 시간, 유실 행 수만 기록되고 실행 전체 분위수가 없다. 결국 전체 p99를 알려면 client_operations.csv를 집계해야 하는데, 고부하에서는 --operation-sampling을 낮추라고 문서가 권고하므로 그때는 정확도가 떨어진다. 부하가 클수록 지연 통계가 부정확해지는 구조다.

2.3 부하 구간과 무부하 구간이 구분되지 않는다

서버는 클라이언트와 독립적으로 --duration만큼 돈다. 이번 실행에서 서버는 76개 샘플을 기록했지만 실제 부하가 걸린 구간은 31개뿐이었다(핸들러 지연이 0이 아닌 행 기준). 나머지 45개 행은 처리량 0이다. 이 행들이 그대로 평균에 섞이면 처리량이 절반 이하로 왜곡된다. 램프업 구간도 마찬가지다. 지금은 CSV에 구간을 표시하는 컬럼이 없어 분석 시점에 사람이 elapsed_ms 범위를 눈으로 잘라내야 한다.

C1 지연 히스토그램을 고정 버킷 방식으로 교체 표본을 개별 보관하지 않으므로 기록 비용과 메모리가 표본 수와 무관해졌다. 기록을 스레드별 슬롯으로 나눠 단일 락 경합을 없앴다. 실행 전체 누적과 1초 창을 함께 유지한다.

서버를 클라이언트보다 오래 켜 두면 무부하 구간이 평균을 끌어내린다. 구간 구분이 없을 때는 실제로 낸 처리량의 절반 이하가 보고되고 있었다. 구간 판정이 맞는지도 확인했다. verify01에서 서버는 클라이언트 접속 전 구간을 idle로, 접속이 늘어나는 5초를 rampup으로, 이후를 steady로 판정했다. 클라이언트에 지정한 --ramp-up 00:00:05와 일치한다.

3.6 하위 호환

CSV에 컬럼을 추가했지만 과거 실행 결과도 계속 분석할 수 있다. 분석 뷰가 union_by_name을 쓰고, phase가 없는 행은 unknown으로 채워 부하 구간으로 취급한다. 실제로 구 스키마 실행(probe01)과 신 스키마 실행을 한 데이터베이스에서 함께 조회해 확인했다. 구 실행은 새 요약 항목이 빈 값으로 나올 뿐 집계에서 사라지지 않는다.

4. 단계 2 구현 결과

측정을 믿을 수 있게 되었으니 다음은 부하 자체를 목표대로 거는 일이다. 2.1절에서 지목한 닫힌 루프 구조를 열린 루프로 바꿨다.

항목한 일내용
A1 열린 루프 페이싱 송신 시각을 실행 시작 기준의 절대 일정으로 고정했다. 한 번 늦게 나가도 다음 송신은 원래 예정 시각을 따르므로 오차가 누적되지 않는다. --pacing open|closed로 예전 동작도 남겼고 기본값은 open이다.
A2 동시 요청 지원 본문 앞 8바이트에 상관 ID를 실어 요청과 응답을 짝짓는다. 응답 순서에 의존하지 않는다. --max-in-flight로 깊이를 정하고, 지정하지 않으면 송신 레이트 × 수신 타임아웃으로 잡는다.
A3 송수신 루프 분리 송신과 수신을 독립 루프로 나눴다. 응답 처리가 늦어져도 송신 일정이 밀리지 않는다.

열린 루프는 TCP 바이너리 프로토콜에만 적용된다. UDP와 text-line은 상관 ID를 실을 자리가 없어 닫힌 루프로 남겨 두었다.

4.1 목표 부하를 실제로 거는가

100 클라이언트 × 초당 5요청(목표 500 req/s)으로 같은 조건에서 두 방식을 비교했다. 아래 응답 지연 행은 --slow-receiver-delay-ms 20으로 응답 처리를 인위적으로 늦춘 경우다. 서버가 느려진 상황을 흉내 낸다.

조건페이싱 달성 RPS목표 달성률 최대 동시 요청RTT p99 (ms)
정상closed484.196.8%—1.775

목표 달성. 정상 조건에서 달성률이 96.8%에서 99.9%로 올랐다. 5장이 정한 완료 기준(±1% 이내)을 만족한다. 스케줄 지연 p99는 0µs, 한도에 걸려 건너뛴 송신도 0건이었다.

부하가 줄지 않는다. 응답 처리를 20ms 늦추자 닫힌 루프는 부하가 96.8%에서 84.8%로 떨어졌다. 같은 조건에서 열린 루프는 100.0%를 유지했다. 2.1절이 지목한 "서버가 느려지면 부하도 같이 줄어든다"가 실제로 그러함을, 그리고 그것이 해소되었음을 함께 보여준다.

4.2 닫힌 루프는 지연을 낮게 보고하고 있었다

정상 조건에서 열린 루프의 RTT p99가 5.599ms로, 닫힌 루프의 1.775ms보다 3배 이상 높게 측정됐다. 측정이 나빠진 것이 아니라 부하가 제대로 걸린 것이다.

닫힌 루프는 응답을 받아야 다음 요청을 보내므로 한 연결에 요청이 항상 하나만 떠 있다. 서버 입장에서는 대기 행렬이 생기지 않는다. 열린 루프는 목표 레이트대로 보내므로 응답이 늦어지면 요청이 쌓인다. 실제로 최대 25건이 동시에 떠 있었고, 그 대기 시간이 지연에 반영된다. 실제 게임 클라이언트가 만드는 상황에 가까운 쪽은 후자다.

다만 p99는 실행 간 변동이 크다(3.5절). 위 3배라는 값 자체는 단일 실행 비교이므로 정확한 크기는 반복 실행으로 확인해야 한다. 방향(닫힌 루프가 더 낮게 보고한다)은 동시 요청이 쌓인다는 구조적 이유가 뒷받침한다.

이전 실행과의 비교에 주의

페이싱이 다르면 지연 수치를 직접 비교할 수 없다. 단계 1까지의 실행(probe01, verify0*, repeat0*)은 모두 닫힌 루프다. 변경 전후를 비교할 때는 양쪽의 pacing을 맞춰야 한다. client_summary.csv와 analysis_run_summary에 실제 적용된 값이 기록된다.

4.3 부하를 내지 못할 때 원인을 가린다

열린 루프로 바꾸면 부하가 클라이언트 자원에 직접 부딪힌다(9장 위험 요소). 그래서 "서버가 느린 것"과 "클라이언트가 못 보내는 것"을 구분할 지표를 함께 넣었다.

지표읽는 법
send_schedule_delay_p99_us예정 시각보다 늦게 나간 송신의 지연이다. 크면 클라이언트가 일정을 따라가지 못하고 있다.
send_skipped_in_flight동시 요청 한도에 걸려 보내지 못한 송신 수다. 부하가 조용히 사라지지 않도록 명시적으로 센다.
max_in_flight_observed관측된 최대 동시 요청 수다. 한도에 붙어 있으면 한도를 올려야 한다.

이 세 값이 모두 0에 가까운데 달성률이 낮다면 부하 발생기는 정상이며 다른 원인을 봐야 한다. 위 실측에서는 세 값이 각각 0µs, 0건, 25건이었다. 마지막 값이 한도(25)와 같으므로, 더 높은 레이트로 올릴 때는 --max-in-flight를 함께 올려야 한다.

4.4 부수 소득: 세션 수 계측 버그를 찾았다

열린 루프로 바꾸자 재접속 폭주 시나리오의 자체 테스트가 실패하기 시작했다. "클라이언트가 모두 떠난 뒤 서버의 활성 세션이 0이어야 한다"는 검사였다. 재현해 보니 서버가 이렇게 기록하고 있었다. 

total_connected = 50
total_closed    = 50
active_sessions = 2      ← 맞지 않는다

원인은 active_sessions를 별도 카운터로 증감한 데 있었다. 감소 시 값이 0이면 건너뛰는 방어가 들어 있었는데, 접속과 종료 이벤트는 서로 다른 스레드에서 오므로 순서가 뒤바뀔 수 있다. 활성이 0인 순간에 종료 이벤트가 먼저 도착하면 그 감소가 버려지고, 뒤늦게 도착한 접속 이벤트가 값을 올려 차이가 영구히 남는다.

두 누적 카운터의 차이(total_connected - total_closed)로 구하도록 바꿨다. 이벤트 순서와 무관하게 항상 맞는다.

이 버그는 세션 누수 판정을 망가뜨리고 있었다

analysis_session_leak_check와 analysis_smoke_verdict는 최종 활성 세션이 0인지로 누수를 판정한다. 누수가 없는데도 세션이 남은 것처럼 보고되고 있었으므로, 재접속이 잦은 실행에서는 없는 누수를 있다고 판정했을 것이다.

단계 2의 목표와는 무관한 결함이지만, 부하를 더 정확히 걸게 되자 드러났다. 닫힌 루프는 재접속이 느려 경합 창이 좁았고 그래서 눈에 띄지 않았다.

4.5 검증

자체 테스트 66건 전부 통과했다(기존 60건 + 신규 6건). 빌드 경고 0개. 기본값을 open으로 바꿨는데도 기존 테스트가 모두 통과한다는 것은 부분 전송, 묶음 전송, 게임형 시나리오, 재접속 폭주가 새 경로에서도 동작한다는 뜻이다.

신규 테스트는 다음을 검증한다.

  • 상관 ID 왕복 — 부호화·복호화를 거쳐도 유지되는지, 본문이 충분히 길면 페이로드 크기가 그대로인지, 하트비트처럼 본문이 빈 패킷도 자리를 얻는지
  • 느린 응답에서의 송신 유지 — 열린 루프가 닫힌 루프보다 최소 2배 이상 보내는지. 열린 루프가 존재하는 이유를 그대로 시험한다
  • 동시 요청 한도 — 한도를 넘지 않는지, 넘겨서 건너뛴 송신이 기록되는지

세션 카운터 수정 후 테스트를 3회 연속 돌려 66건 전부 통과함을 확인했다. 간헐적 실패가 아니라 실제 결함이었으므로 반복 확인이 필요했다.

5. 단계 3 구현 결과

측정을 믿을 수 있고 목표 부하도 걸 수 있게 되었으니, 다룰 수 있는 상황의 범위를 넓혔다.

항목한 일내용
B1 UDP·text-line 서버 추가 서버가 세 리스너를 함께 띄운다(--text-port, --udp-port). 라이브러리에 구분자 기반 필터가 없어 text-line 필터를 직접 구현했다. 세 리스너는 계측기를 공유한다.
B3 이상 상황 시나리오 순간 폭주(--scenario burst), 비정상 종료(--abort-percent), 대용량 페이로드(--payload huge·mixed-huge)를 추가했다.
A5 대규모 연결 대비 실행 시작 시 스레드풀 최소 워커를 미리 확보한다. 연결 실패가 임시 포트 고갈 같은 부하 발생기 쪽 한계에서 온 것인지 구분해 기록한다.

5.1 실행할 수 없던 옵션이 실행된다

--transport udp와 --protocol text-line은 오래 전부터 클라이언트에 있었지만 받아 줄 서버가 없어 쓸 수 없는 옵션이었다(2.4절). 이제 --text-port와 --udp-port로 리스너를 열면 같은 프로세스에서 함께 돈다. 

dotnet run --project Test\LoadTest\SuperSocketLite.LoadTest.Server -- \
  --port 2500 --text-port 2501 --udp-port 2502 ...

LoadTestServer listening on port 2500.
  text-line listener on port 2501
  UDP listener on port 2502

세 리스너는 하나의 계측기를 공유한다. GC·메모리·CPU는 프로세스 단위 값이라 리스너마다 따로 재는 것이 의미가 없고, 세션과 요청 수는 합산해 보는 편이 서버 전체 부하를 읽기 쉽기 때문이다.

UDP와 text-line은 닫힌 루프로 남는다

두 프로토콜에는 요청과 응답을 짝지을 상관 ID를 실을 자리가 없다. 응답 순서에 의존하지 않으려면 프로토콜 자체에 필드를 넣어야 하므로, --pacing open을 지정해도 이 둘은 닫힌 루프로 동작한다. 열린 루프가 필요하면 프로토콜 변경 여부를 먼저 판단해야 한다.

5.2 이상 상황에서 서버가 견디는가

시나리오확인한 것
순간 폭주 기본 레이트 위에 주기마다 한 뭉치를 얹는다. 열린 루프가 들어왔기 때문에 그 뭉치가 응답 대기에 막히지 않고 실제로 몰려 나간다. 자체 테스트에서 폭주 실행이 같은 조건 기본 실행보다 2배 넘게 보내는 것을 확인했다.
비정상 종료(RST) 클라이언트가 FIN 대신 RST로 끊어도 서버 exception_total이 0이고 최종 active_sessions가 0으로 돌아온다. 모바일 환경에서 흔한 끊김이라 서버가 이 경로에서 무너지면 안 된다.
대용량 페이로드 약 32KB 요청이 타임아웃 없이 왕복한다.
프로토콜의 최대 본문 크기는 32,762바이트다

처음에 huge를 60KB로 잡았더니 요청이 하나도 나가지 않았다. 패킷 헤더의 totalSize가 Int16이라 헤더를 포함해 32,767바이트가 상한이기 때문이다. 그보다 큰 페이로드는 부호화 단계에서 예외가 난다. huge는 이 한계에 붙여 잡았다. 더 큰 요청을 다루려면 프로토콜의 길이 필드부터 바꿔야 한다.

5.3 부하 발생기가 한계에 닿았는지 구분한다

열린 루프는 클라이언트 자원을 더 쓴다(10장 위험 요소). 그래서 실행 시작 시 스레드풀 최소 워커를 미리 확보한다. 스레드풀이 워커를 늘리는 속도는 초당 한두 개 수준이라, 수천 클라이언트가 한꺼번에 뜨면 그 증가를 기다리느라 램프업이 길어지고 송신 일정도 밀린다.

연결 실패도 원인을 나눠 기록한다. 임시 포트 고갈·소켓 수 한계·버퍼 부족은 서버가 거부한 것이 아니라 부하 발생기 머신이 한계에 닿은 것이므로, local_resource_exhaustion으로 따로 센다. 이 값이 0이 아니면 클라이언트 수를 줄이거나 여러 머신에 나눠야 한다는 신호다.

5.4 하지 않은 것: 서버 계측 확장(C5)

송신 큐 깊이와 SmartPool 사용률은 이번에 넣지 못했다.

ChannelSendingQueue에 Count가 있지만 세션 인터페이스로 노출되지 않고, SmartPool은 크기를 조회할 방법 자체가 없다(Push/TryGet뿐). 이 지표를 얻으려면 라이브러리에 공개 API를 추가해야 하는데, 이는 부하 테스트 툴킷 개선이라는 이번 작업 범위를 넘어 라이브러리의 공개 표면을 바꾸는 일이다.

5.5 검증

자체 테스트 71건 전부 통과했다(단계 2의 66건 + 신규 5건). 빌드 경고 0개. 신규 테스트는 text-line 서버 왕복, UDP 서버 왕복, 폭주 시나리오의 송신량, RST 종료 후 서버 상태, 대용량 페이로드 왕복을 검증한다.

수동 확인은 이런 실수에 약하다

UDP를 처음 수동으로 확인했을 때 응답이 하나도 오지 않아 코드 문제로 의심했다. 그러나 원인은 서버 실행 시간이 이미 끝난 뒤에 클라이언트를 돌린 것이었다. 변수를 하나씩 되돌려 확인한 끝에 코드는 정상이었음을 알았다. 같은 실수를 반복하지 않도록 두 프로토콜 모두 통합 테스트로 고정했다.

6. 단계 4 구현 결과

측정을 믿을 수 있고, 목표 부하를 걸 수 있고, 다룰 상황도 넓어졌다. 마지막은 이것을 매번 손으로 돌리지 않아도 되게 만드는 일이다.

항목한 일내용
D1 HTML 리포트 생성기 신규 프로젝트 LoadTest.Report. CSV를 읽어 파일 하나로 열리는 HTML을 만든다. 판정·지표·시계열을 담고 차트는 인라인 SVG라 외부 자원을 참조하지 않는다.
D2 기준 실행 비교 --baseline과 --run이 접두사로 실행을 묶는다. 지표별 중앙값으로 비교해 꼬리 지연의 실행 간 변동을 걷어낸다.
D3 임계값 판정 합격 조건을 thresholds.json으로 분리했다. 위반 시 --fail-on-regression으로 종료 코드 1을 반환한다.
E1·E2·E3 실행 러너와 매트릭스 run-loadtest.ps1이 서버 기동부터 리포트까지 한 번에 돌린다. run-matrix.ps1이 시나리오 여섯 조합을 훑는다.

6.1 회귀를 실제로 잡아내는가

판정 도구가 성능 저하를 잡는지 확인했다. 단계 1까지의 실행(repeat01~03, 닫힌 루프)을 기준으로 삼고 단계 2 이후의 실행(open01, 열린 루프)을 대상으로 비교했다. 

  PASS  오류율          0.000% (상한 0.100%)
  PASS  목표 레이트 달성   99.9% (하한 95.0%)
  PASS  서버 예외        0건
  PASS  세션 정리        종료 후 활성 세션 0개
  ----  페이싱 일치       기준 'unknown' 대 대상 'open'. 페이싱이 다르면 지연을 견줄 수 없다.
  FAIL  p99 지연        1.135 → 5.599 ms (+393.3%, 상한 +10%)
  FAIL  p99.9 지연      3.631 → 11.711 ms (+222.5%, 상한 +25%)
  PASS  처리량          483.3 → 500.3/s (103.5%, 하한 95%)
  PASS  메모리 증가       13.9 → 13.9 MB (차이 0 MB, 상한 +50 MB)

판정: 불합격          (--fail-on-regression 종료 코드 1)

지연 증가를 정확히 잡아냈고, 동시에 그 비교가 성립하지 않는다는 것도 함께 알렸다. 페이싱이 다르면 닫힌 루프 쪽이 부하를 덜 걸어 지연이 낮게 나오므로, 이 393%는 성능 저하가 아니라 측정 방식의 차이다. 판정만 내리고 이유를 숨겼다면 잘못된 결론으로 이어졌을 것이다.

반대로 같은 페이싱끼리(repeat01~03 대 verify01~02) 비교하면 아홉 항목이 모두 통과하고 종료 코드 0을 반환한다.

6.2 꼬리 지연은 중앙값으로 본다

3.5절에서 확인한 대로 p99는 실행 간 44%, p99.9는 124%까지 흔들린다. 한 번의 실행으로 회귀를 판정하면 그 변동을 성능 변화로 오인한다. 그래서 같은 접두사의 실행을 묶어 지표마다 중앙값을 취한다.

다만 모든 지표에 중앙값을 쓰지는 않는다. 서버 예외와 세션 누수는 최악값을 남긴다. 세 번 중 한 번 예외가 났다면 중앙값은 0이 되어 사고가 묻히기 때문이다.

6.3 실행 러너

run-loadtest.ps1이 서버 기동 → 리슨 확인 → 클라이언트 실행 → 서버 정리 → 리포트를 한 번에 한다. -Repeat 3으로 같은 조건을 반복하면 base01·base02·base03처럼 번호가 붙어 그대로 비교 묶음이 된다.

리슨 확인을 넣은 이유

고정 시간 대기로는 기동이 느린 날 클라이언트가 먼저 붙어 실패한다. 반대로 서버 실행 시간이 끝난 뒤 클라이언트가 도는 일도 생긴다. 5.5절에 적었듯 실제로 그 때문에 정상 동작을 결함으로 오인했다. 러너는 포트가 열릴 때까지 기다린 뒤에 클라이언트를 띄우고, 클라이언트가 끝나면 서버를 확실히 내린다.

run-matrix.ps1은 정상 부하(echo·game-like)와 이상 상황(burst·mixed-huge·abort·reconnect-storm) 여섯 조합을 차례로 돌리고 하나의 리포트로 모은다. 조합마다 포트를 다르게 잡아 앞선 실행의 TIME_WAIT 소켓과 부딪히지 않게 한다.

실제로 여섯 조합을 돌려 서버 예외 0건, 세션 누수 0건으로 완주하는 것을 확인했다. 10장이 정한 단계 3 검증 기준(이상 상황에서 서버가 예외 없이 견디는지)이 이것으로 채워진다.

6.4 검증

자체 테스트 80건 전부 통과했다(단계 3의 71건 + 신규 9건). 빌드 경고 0개. 신규 테스트는 리포트 쪽 로직을 덮는다.

  • 중앙값 집계 — 지표별 중앙값이 맞는지, 예외·세션 누수는 최악값이 남는지
  • 판정 — 지연 회귀·처리량 하락·낮은 달성률이 불합격이 되는지, 임계값 안이면 통과하는지
  • 페이싱 불일치 — 비교가 성립하지 않을 때 보류로 표시되는지
  • CSV 적재 — 서버와 클라이언트 디렉토리가 run_id로 하나의 실행으로 묶이는지, 정상 구간만 평균하는지
  • 리포트 자립성 — 만들어진 HTML이 외부 자원을 참조하지 않는지

9. 단계 계획

순서의 원칙은 하나다. 측정을 믿을 수 있게 만드는 일이 가장 먼저다. 부하를 더 정교하게 걸어도, 그 결과를 정확히 읽지 못하면 의미가 없다. 반대로 측정이 정확해지면 지금 구조로도 얻는 값이 즉시 좋아진다.

단계주제항목 이 단계가 끝나면
1 완료 측정 신뢰성 C1 · C2 · C3 · C4 · D4 · A4 실행 전체 p99가 정확히 남고, 정상 구간만 집계되며, 오류 집계에 노이즈가 없다. 지금 수준의 부하로도 결과를 신뢰할 수 있게 된다.
2 완료 부하 정확도 A1 · A2 · A3 목표 레이트를 실제로 달성하고, 달성하지 못하면 원인이 지표로 구분된다. 지연 시간이 과소평가되지 않는다.
3 대부분 커버리지 B1 · B2 · B3 · A5 · C5 UDP·text를 포함한 세 전송 방식과 이상 상황 시나리오를 실행할 수 있고, 서버 내부 큐·풀 지표를 본다.
4 대부분 자동화 D1 · D2 · D3 · E1 · E2 · E3 · B4 · C6 명령 하나로 실행부터 회귀 판정까지 끝난다. 개선 작업마다 before/after를 손쉽게 비교한다.
단계 1만 끝나도 실질적 가치가 있다

단계 1은 기존 구조를 크게 바꾸지 않는 국소 수정이 대부분이다. 이것만으로 TODO.md의 개선 항목을 수치로 검증할 수 있게 된다. 단계 2 이후는 더 넓은 상황을 다루기 위한 확장이다.

10. 검증 방법

각 단계의 완료는 다음으로 확인한다.

단계확인 방법
단계 1 같은 파라미터로 3회 반복 실행했을 때 정상 구간 처리량과 전체 p99가 재현되는지 확인한다. client_operations.csv를 전량 기록한 실행과 1%만 샘플링한 실행의 요약 p99가 일치하는지 비교한다(C1·C2 검증). 서버 CSV에 처리량 0인 행이 정상 구간으로 분류되지 않는지 확인한다(C3·C4 검증).
단계 2 목표 레이트 대비 달성률이 정상 구간에서 99% 이상인지 확인한다. 서버에 인위적 지연을 넣었을 때 부하량이 유지되고 지연 시간이 실제로 증가하는지 본다(열린 루프 동작 확인).
단계 3 UDP·text 시나리오가 실제로 완주하고 CSV가 생성되는지 확인한다. 이상 상황 시나리오에서 서버가 예외 없이 견디는지 본다.
단계 4 의도적으로 성능을 떨어뜨린 빌드에 대해 판정 도구가 불합격과 0이 아닌 종료 코드를 반환하는지 확인한다.

11. 위험 요소

위험대응
클라이언트가 먼저 병목이 된다 열린 루프로 바꾸면 부하가 클라이언트 자원에 직접 부딪힌다. 송신 지연과 backlog를 지표로 남겨 "서버가 느린 것"과 "클라이언트가 못 보내는 것"을 구분한다. 이 지표 없이 열린 루프로 가면 안 된다.
단일 머신의 연결 수 한계 Windows 임시 포트와 TIME_WAIT 때문에 한 머신에서 낼 수 있는 연결 수에 한계가 있다. 이미 갖춰진 machine_id 기반 분산 실행 규약을 활용하고, 한계 도달을 오류가 아니라 명시적 경고로 보고한다.
계측이 측정 대상을 흔든다 서버 계측이 측정 대상 프로세스 안에서 돈다. C6로 오버헤드를 수치화하고, 고부하에서는 이벤트 기록 비율을 낮춘다.
CSV 스키마 변경의 파급 phase 등 컬럼 추가는 DuckDB SQL과 기존 실행 결과에 영향을 준다. 분석 뷰가 union_by_name을 쓰므로 컬럼 추가는 견디지만, 판정 로직은 함께 갱신해야 한다(D4를 단계 1에 넣은 이유).
측정 환경의 변동 백신 실시간 검사, 다른 프로세스, 전원 설정이 결과를 흔든다. 실행 환경 정보를 결과에 함께 기록하고, 비교는 같은 환경의 실행끼리만 한다.

지금까지 확인된, 이후 설계에 반영할 사항
  • 꼬리 지연(p99·p99.9)은 실행 간 변동이 크다(3.5절). 회귀 판정은 단일 실행이 아니라 여러 회 실행의 중앙값을 기준으로 해야 한다. 단계 4의 D2·D3 설계에 반영한다.
  • CSV 스키마 변경은 하위 호환이 유지되는 것으로 확인됐다(3.6절). 이후 컬럼 추가도 같은 방식(끝에 추가 + union_by_name)으로 진행한다.
  • 페이싱이 다른 실행은 지연 수치를 직접 비교할 수 없다(4.2절). 판정 도구는 비교 대상 두 실행의 pacing이 다르면 경고해야 한다.
  • 동시 요청 한도의 기본값(레이트 × 타임아웃)이 실측에서 한도에 닿았다(4.3절). 더 높은 레이트를 쓸 때는 --max-in-flight를 함께 올리거나 기본 산정식을 재검토한다.
  • 프로토콜의 최대 본문 크기는 32,762바이트다(5.2절). 더 큰 요청을 다루려면 헤더의 길이 필드부터 바꿔야 한다.
아직 판단이 필요한 사항
  • 라이브러리 공개 API를 넓혀도 되는지 — 송신 큐 깊이와 풀 사용률(C5)을 보려면 필요하다. TODO.md의 송신 경로 개선을 수치로 검증하려면 결국 있어야 하는 지표다.
  • 목표로 하는 최대 동시 접속 규모 (단일 머신 한계를 넘으면 분산 실행 준비가 필요하다)
  • UDP·text 프로토콜에 상관 ID 필드를 넣어 열린 루프를 적용할지, 닫힌 루프로 둘지

닫힌 루프 존치 여부는 --pacing 옵션으로 둘 다 남기는 것으로 정리했다. 기존 실행 결과와의 비교 가능성을 지키기 위해서이며, 기본값은 open이다.
