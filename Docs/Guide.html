1. What the library does for you

Write a socket server by hand and you keep solving the same problems: an async accept loop, reusing SocketAsyncEventArgs, the fact that TCP is a stream with no packet boundaries, the race when several threads try to write to the same session at once, and data getting cut off mid-send during shutdown. SuperSocketLite handles all five of these for you.

There are only two places you fill in.

1. Receive filter

The rule that decides "this much is one packet" out of a byte stream. You write it by subclassing IReceiveFilter.

2. Request handler

What to do once you've received one packet. You attach it to the NewRequestReceived event.

The smallest possible server

A server that echoes back a protocol consisting of a 4-byte length prefix followed by a body.

// The type representing one request.
// Body points straight at the receive pipe's memory, and the filter hands back the same instance every time.
public sealed class MyRequestInfo : IRequestInfo
{
    public string Key => string.Empty;
    public ReadOnlySequence<byte> Body { get; private set; }
    public void Set(ReadOnlySequence<byte> body) => Body = body;
}

// Reads the 4-byte length prefix and reports how big the body is.
public sealed class MyReceiveFilter : FixedHeaderReceiveFilter<MyRequestInfo>
{
    private readonly MyRequestInfo _reusable = new();

    public MyReceiveFilter() : base(4) { }

    protected override int GetBodyLengthFromHeader(ReadOnlySequence<byte> header)
    {
        Span<byte> buf = stackalloc byte[4];
        header.CopyTo(buf);                       // safe even if the header spans segments
        return BinaryPrimitives.ReadInt32LittleEndian(buf);
    }

    protected override MyRequestInfo ResolveRequestInfo(
        ReadOnlySequence<byte> header, ReadOnlySequence<byte> body)
    {
        _reusable.Set(body);
        return _reusable;
    }
}

public sealed class MySession : AppSession<MySession, MyRequestInfo> { }

public sealed class MyServer : AppServer<MySession, MyRequestInfo>
{
    public MyServer() : base(new DefaultReceiveFilterFactory<MyReceiveFilter, MyRequestInfo>()) { }
}

Starting it up is just as short.

var config = new ServerConfig
{
    Ip = "Any", Port = 2012, MaxConnectionNumber = 1000,
    Mode = SocketMode.Tcp, Name = "EchoServer"
};

var server = new MyServer();
server.NewRequestReceived += (session, request) =>
{
    if (request.Body.IsSingleSegment)
        session.SendCopied(request.Body.FirstSpan);
    else
        session.SendCopied(request.Body.ToArray());   // rare: the packet spans pipe segments
};

server.Setup(new RootConfig(), config, logFactory: new ConsoleLogFactory());
server.Start();
An important choice has already been made here. The handler above responds right where it stands and returns. That's why it can reuse the request instance and skip copying the body. A server that hands packets off to another thread is a different story — see chapter 4.

2. Receiving — from bytes to a request

TCP is a stream. There's no guarantee the server receives a client's packet in one piece — three packets can just as easily arrive glued together. So something has to cut complete packets out of "the bytes received so far," and that's the receive filter's job.

Here's the flow on the library side. Think of the dot as data and follow it.

A filter does exactly two things

With FixedHeaderReceiveFilter<T> you only fill in two methods.

MethodQuestion it answers
GetBodyLengthFromHeader(header) I've seen the header. How many more bytes should the body be?
ResolveRequestInfo(header, body) It's all here. What request object should this become?

If there isn't enough data yet, you don't have to do anything. The library figures out "not yet" on its own and leaves the data sitting in the pipe. There's no buffer-splicing or offset math to do by hand.

header and body can span multiple segments. Don't read them straight off header.First.Span — use CopyTo(Span). That's why the example above copies into a stackalloc buffer before reading.

The full step-by-step flow is in the receive flow diagram.

3. Sending — from a response to the socket

On the send side, what the library solves for you is "what happens when several threads write to the same session at once." The answer is simple: anyone can enqueue, but exactly one thread is ever actually writing to the socket.

Which Send to use

SituationAPIWhy
An ordinary one-off response SendCopied(span) Copies into the library's pooled buffer. You can reuse your own buffer right away.
The same content to many recipients Send(byte[], 0, len) Shares the array without copying. In exchange, don't modify that array after sending.
A slow client, and it's fine to wait SendAsync(memory, ct) Waits asynchronously instead of spinning when the queue is full. Set a timeout with a cancellation token.
Just drop it if the queue is full TrySendCopied(span) Returns false. Never throws.
There's a fixed order of operations after a timeout. If you catch TimeoutException and plan to close the session, you must call session.SendEndWhenSendingTimeOut() first, then Close(). That call releases the InSending flag. Skip it and that session never closes.

The step-by-step flow is in the send flow diagram.

4. The one contract you must keep

There's exactly one decision in this library that determines both performance and safety at the same time: does the packet get fully handled inside the handler, or does it get handed off to another thread?

Why you can pick the left side

The library calls your handler synchronously and only advances the pipe after the handler fully returns. So the body's memory is guaranteed to stay alive for as long as the handler is running. There's also exactly one filter per session, and the next packet on that same session is only parsed after this handler finishes.

The constraint that comes with it: once the handler returns, that request object and its body are no longer valid. Don't store them in a field, capture them in a lambda, or push them onto another thread's queue.

Break this and it still compiles, and it usually still works under light load. Data only corrupts once load is high enough for the pipe's buffer to actually get reused, which makes it a very hard bug to track down. If you need to keep a value, deserialize or copy it inside the handler.

When to pick the right side

If you're handing packets off to a logic thread, copying the body is unavoidable. What you can still avoid is the allocation — borrow from ArrayPool<byte>.Shared instead of new byte[]. The rule here is simple: pick one place to return it, and only return it there. Tutorials/PvPGameServer is built this way — everything is returned in exactly one finally block inside PacketProcessor.Process().

The full reasoning behind both approaches, and the actual measured effect, are in the GC and Copy Minimization guide (Korean).

5. A tour of the Tutorials examples

The examples fall into three broad groups. The fork you just saw above is exactly where the groups split. The full map is in the reading-order diagram.

Basics — the echo server family

All of these respond directly inside the handler and stop there. Each is written around reusing a single request instance.

EchoServer synchronous

Start here · 5-byte header (2-byte total length + 2-byte packet ID + 1 byte reserved)

The smallest setup that echoes back whatever it receives. ReceiveFilter.cs holds the request type and the filter together, and MainServer.cs holds the server config and the handler. Three files, total — it's the clearest picture of the minimum you need to use the library.

  • Serializes the response into a stackalloc buffer and sends it with SendCopied.
  • The filter reuses one request instance — receiving a packet allocates nothing.

Run it: build, then Tutorials/00_server_bins/run_EchoServer.bat · client is EchoClient

EchoServer_NuGet synchronous

The exact same server as EchoServer · references the published package instead of the repo

Identical code and protocol to EchoServer — the only difference is one line in the .csproj: a PackageReference to the SuperSocketLite2 NuGet package instead of a ProjectReference to the local library project. Copy this folder out of the repository and it still builds, because it doesn't need the repository at all.

Run it: build, then Tutorials/00_server_bins/run_EchoServer_NuGet.bat (port 32453) · client is EchoClient

EchoServerEx synchronous

EchoServer + command-line arguments + logging

The same echo server with two things a real deployment needs. Settings like port and max connections come from command-line arguments (CommandLineParser), and logging goes through NLog. This is also where a dispatch map keyed by packet ID first shows up — you need one once the number of packet types grows.

Run it: run_EchoServerEx.bat

EchoServer_GenericHost synchronous

Running as a service on top of .NET Generic Host

Wraps the server in an IHostedService so Generic Host manages its lifetime. Configuration comes from appsettings.json, and logging/DI go through the host. This is the shape most real deployments take, so if your shop standardizes on Generic Host, start here.

Protocols and ports

BinaryPacketServer synchronous

An example of designing your own packet boundaries · 12-byte request header

The header carries a packet ID (4 bytes), two values, and a body length (4 bytes). It shows GetBodyLengthFromHeader reading the length from a specific offset in the header.

This example's request header (12 bytes) and response header (8 bytes) have different formats — intentionally. Don't let it confuse you when reading the code.

MultiPortServer synchronous

How one process can listen on several ports

Creates two server instances and calls Start() on each with a different port. This is the shape to use when you want to separate an internal port from an external client-facing port. Give each port its own filter and request type if they need different protocols.

SimpleUDPServer synchronous

Deciding what identifies a session when there's no connection, as in UDP

UDP has no connection, so the server has to decide for itself "whose datagram is this." This example's request type inherits from UdpRequestInfo, and it finds the session using a session ID embedded directly in the payload. That way a client keeps the same logical session even across a NAT rebind. Without that inheritance, the remote endpoint is used as the key instead.

This example is a minimal skeleton with no receive handler registered. It's here to show how the filter parses a datagram — don't expect it to echo anything if you just run it as-is.

sendFailTestServer synchronous

What happens if you keep sending to a client that isn't receiving

Sets SendTimeOut, SendingQueueSize, and SendBufferSize small and keeps pushing packets on a timer to deliberately reproduce TimeoutException. Worth seeing once before you meet it in production.

The important part is the order after catching the exception. 

catch (TimeoutException ex)
{
    // This call releases the InSending flag. Skip it and the session never closes.
    session.SendEndWhenSendingTimeOut();
    session.Close();
}

Game server shapes — examples that hand off to a logic thread

From here on, game logic doesn't run on the receive thread. The packet is enqueued and a separate thread pulls it out and processes it, which means the body has to be copied.

ChatServer thread handoff

The simplest handoff · a single logic thread

The receive handler copies the packet into a ServerPacketData, pushes it onto a BufferBlock queue, and returns immediately. A single PacketProcessor thread drains that queue and handles login, joining a room, and chat. Because logic runs on exactly one thread, room and user data structures need no locks — that's the whole point of this example.

Broadcasting lives in Room.cs. It builds a single packet array and hands that same array to every session in the room — it doesn't copy once per recipient.

ChatServerEx thread handoff

ChatServer + several logic threads + a DB worker

Same feature set as ChatServer, different processing structure. Rooms are assigned to threads so that each thread only ever touches its own rooms — a common way to get parallelism without locks. PacketDistribute decides which processor a packet goes to.

Database access gets handed off again: a DB worker thread processes it and turns the result back into a packet on the shared queue. It's effectively a two-stage handoff, so logic threads never block waiting on a DB response.

PvPGameServer thread handoff

MemoryPack serialization · room-based matches · an example that actually applies ArrayPool

Serializes with MemoryPack and pushes the whole request object onto the logic thread's queue. It's also the repository's real example of buffer pooling in practice — the receive filter borrows from ArrayPool, and it's returned in exactly one place: the finally block of PacketProcessor.Process().

An array borrowed from the pool can be larger than what you asked for. That's why the length is tracked as DataSize rather than Data.Length, and deserialization is handed DataSpan. This is the detail people miss most often when imitating pooling.

GameServer_MoDedicated / MoDedicated2 thread handoff

The shape of a dedicated game server

Structurally the same as ChatServer (queue + logic thread). The difference is a separate game update loop. MoDedicated2 runs several update threads (4 by default) and assigns rooms across them. Worth a look when you're deciding how to split packet processing from the game tick.

GateServer_GameServer thread handoff

A front-end gate server that receives and hands off to the back end

Clients only ever connect to the gate, and the gate forwards packets to the game server behind it. This layout absorbs connection count and authentication up front, so the game server can focus purely on logic. CommonLib holds the packet definitions the two servers share.

This example is mostly skeleton. No packet handlers are registered, so received packets are only logged. Read it for the structure.

Client examples

Testing a server needs a matching client. EchoClient (WinForms) works with most of the echo family, ChatClient (WPF) pairs with the chat servers, and PvPGameServer_Client pairs with the PvP server. All three implement their own packet-assembly buffer (PacketBufferManager), so you can also see how the client side cuts up a TCP stream.
