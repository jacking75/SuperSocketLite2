1. 빌드하기

요구 사항

  • .NET 10.0 SDK
  • Windows 또는 Linux — 비동기 소켓 엔진(SocketAsyncEventArgs/IOCP)과 TCP keep-alive 옵션 모두 크로스플랫폼입니다.

라이브러리만 빌드

cd SuperSocketLite
dotnet build -c Release

결과물은 저장소 루트의 bin/net10.0/에 쌓입니다 — SuperSocketLite.csproj의 OutputPath가 ..\bin으로 잡혀 있기 때문입니다(csproj 기준 한 단계 위).

현재 소스의 패키지 버전은 SuperSocketLite.csproj 기준 0.91.0입니다. 전체 솔루션(SuperSocketLite2.slnx)을 빌드하면 저장소에 커밋되어 있는 예제 실행 파일( Tutorials/*/00_server_bins 등)도 함께 갱신됩니다. 라이브러리 코드만 검증할 때는 SuperSocketLite/SuperSocketLite.csproj와 필요한 테스트 프로젝트만 빌드하면 이 문제가 없습니다.

참조 방법 — 별도 NuGet 패키지 SuperSocketLite2

이 저장소의 코드(System.IO.Pipelines 기반 수신, Channel<T> 기반 송신)는 SuperSocketLite2라는 별도의 NuGet 패키지로 배포됩니다 — NuGet.org의 기존 SuperSocketLite 패키지(여전히 재작성 이전의 .NET 9 라인)와는 다른, 독립된 패키지 ID입니다. 이 저장소의 변경은 기존 패키지에 영향을 주지 않습니다. 

dotnet add package SuperSocketLite2

첫 릴리스가 올라가기 전까지는 소스를 내려받아 프로젝트 참조로 씁니다.

git clone https://github.com/jacking75/SuperSocketLite2.git

  <ProjectReference Include="..\SuperSocketLite2\SuperSocketLite\SuperSocketLite.csproj" />

라이브러리 자체를 검증하는 회귀 테스트와, 실제 TCP/UDP 트래픽을 서버에 흘려 처리량·지연을 재는 부하 테스트 도구가 저장소에 함께 있습니다. 둘 다 xUnit이 아니라 자체 러너입니다.

2. 최소 서버 만들기

채울 곳은 두 군데뿐입니다 — 패킷 경계를 정하는 수신 필터와, 패킷 하나를 받았을 때 할 일인 요청 핸들러. 아래는 4바이트 길이 프리픽스 뒤에 본문이 오는 프로토콜을 그대로 에코하는, 빌드하면 바로 도는 최소 서버입니다. 

// EchoProtocol.cs
using System.Buffers;
using System.Buffers.Binary;
using SuperSocketLite.SocketBase;
using SuperSocketLite.SocketBase.Protocol;
using SuperSocketLite.SocketEngine.Protocol;

// 요청 하나를 나타내는 타입. Body는 수신 파이프의 메모리를 그대로 가리키고,
// 필터가 인스턴스를 돌려 쓰므로 패킷을 받는 데 드는 할당이 없다.
// 단, 핸들러가 리턴하면 이 인스턴스와 Body는 더 이상 유효하지 않다 (7.4절 참고).
public sealed class MyRequestInfo : IRequestInfo
{
    public string Key => string.Empty;
    public ReadOnlySequence<byte> Body { get; private set; }
    public void Set(ReadOnlySequence<byte> body) => Body = body;
}

// 4바이트 길이 프리픽스를 읽고 본문 크기를 알려 준다.
public sealed class MyReceiveFilter : FixedHeaderReceiveFilter<MyRequestInfo>
{
    private readonly MyRequestInfo _reusable = new();

    public MyReceiveFilter() : base(4) { }

    protected override int GetBodyLengthFromHeader(ReadOnlySequence<byte> header)
    {
        Span<byte> buffer = stackalloc byte[4];
        header.CopyTo(buffer);                       // 헤더가 조각에 걸쳐 있어도 안전하다
        return BinaryPrimitives.ReadInt32LittleEndian(buffer);
    }

    protected override MyRequestInfo ResolveRequestInfo(
        ReadOnlySequence<byte> header, ReadOnlySequence<byte> body)
    {
        _reusable.Set(body);
        return _reusable;
    }
}

public sealed class MySession : AppSession<MySession, MyRequestInfo> { }

public sealed class MyServer : AppServer<MySession, MyRequestInfo>
{
    public MyServer() : base(new DefaultReceiveFilterFactory<MyReceiveFilter, MyRequestInfo>()) { }
}
// Program.cs
using SuperSocketLite.SocketBase;
using SuperSocketLite.SocketBase.Config;
using SuperSocketLite.SocketBase.Logging;

var config = new ServerConfig
{
    Ip = "Any",
    Port = 2012,
    MaxConnectionNumber = 1000,
    Mode = SocketMode.Tcp,
    Name = "EchoServer"
};

var server = new MyServer();

server.NewRequestReceived += (session, request) =>
{
    if (request.Body.IsSingleSegment)
        session.SendCopied(request.Body.FirstSpan);
    else
        session.SendCopied(request.Body.ToArray());   // 드묾: 패킷이 파이프 조각에 걸친 경우
};

if (!server.Setup(new RootConfig(), config, logFactory: new ConsoleLogFactory()))
{
    Console.WriteLine("서버 설정에 실패했습니다.");
    return;
}

server.Start();
Console.WriteLine("2012 포트에서 대기 중. 아무 키나 누르면 종료합니다...");
Console.ReadKey();
server.Stop();
그대로 실행 가능한 프로젝트가 Tutorials/EchoServer에 있습니다. 계층 구조와 애니메이션으로 본 수신·송신 흐름은 안내서 1~3장에, 어느 튜토리얼부터 볼지는 예제 읽는 순서에 있습니다.

3. 무엇을 보낼까 — Send API

네 가지 송신 API는 복사 여부와 큐가 찼을 때의 동작이 다릅니다. 상황에 맞는 것을 고르세요.

메서드복사 여부언제 쓰나
Send(byte[], offset, length) / TrySend Zero-copy — 라이브러리가 배열을 참조로 들고 있는다 전송이 끝날 때까지 다시 건드리지 않을 버퍼가 있을 때
SendCopied(ReadOnlySpan<byte>) / TrySendCopied 풀 버퍼로 복사 호출 즉시 내 버퍼를 재사용해야 할 때(재사용 스크래치 버퍼 등)
SendAsync(ReadOnlyMemory<byte>, CancellationToken) 배열 기반 메모리면 zero-copy 큐가 찼을 때 스핀 대신 await로 기다리고 싶을 때. SendTimeOut은 적용되지 않고 취소는 CT로 건다
Send(IList<ArraySegment<byte>>) 리스트 자체는 enqueue 시 복사(배열은 공유) 여러 세그먼트를 한 논리적 메시지로 보낼 때 — 호출 직후 리스트는 재사용 가능
TrySend/TrySendCopied는 세션이 닫혔거나 큐가 찼을 때 예외 없이 false를 돌려줍니다. 반면 Send/SendCopied는 ServerConfig.SendTimeOut까지 기다리다가 TimeoutException을 던집니다 — 이 예외를 잡은 뒤의 처리 순서는 7.6절을 반드시 보세요.

4. 주요 설정

ServerConfig는 Port, MaxConnectionNumber, ReceiveBufferSize, SendTimeOut, TCP keep-alive, 유휴 세션 정리 같은 보통의 항목 외에 알아 둘 만한 옵션이 몇 개 더 있습니다.

설정기본값용도
ReceiveInlineOnIocpThread true 수신 파이프 전진을 스레드풀로 넘기지 않고 IOCP 완료 스레드에서 바로 한다 — 패킷마다 스레드 전환과 Task 할당 2회를 줄인다.
PreAllocateSAEA / MinPoolSize true / 100 풀링된 SocketAsyncEventArgs를 시작 시 미리 만들어 accept 지연을 최소화하거나, MinPoolSize부터 필요할 때마다 늘린다.
MaxReceivePipeBufferSize 65536 수신 파이프의 backpressure 임계값. MaxRequestLength를 넘기지 않도록 자동으로 보정된다.
SyncSessionConnectedEvent false NewSessionConnected를 accept 경로에서 동기 호출해 "connected → 첫 요청" 순서를 구조적으로 보장한다. 대신 핸들러를 가볍게 유지해야 한다.
AcceptLoopCount 1 같은 리스닝 소켓에서 accept 루프를 여러 개 동시에 돌린다 — 재접속 폭주를 흡수할 때 유용하다.
UseZeroByteReceive false 유휴 세션이 실제 수신 버퍼를 들고 있는 대신 0바이트 수신으로 대기한다 — 대부분 조용한 세션이 많은 서버에서 유휴 연결 메모리를 줄인다.
KeepAliveRetryCount 5 연결을 끊긴 것으로 볼 때까지 응답 없는 keep-alive probe를 몇 번 보낼지. 0 이하면 OS 기본값을 그대로 둔다.
위 표의 네 항목(ReceiveInlineOnIocpThread, SyncSessionConnectedEvent, MaxReceivePipeBufferSize, KeepAliveRetryCount)은 IServerConfig 인터페이스에는 없고 ServerConfig 클래스에만 있습니다. 설정 객체를 인터페이스 타입 변수로 들고 있다면 config as ServerConfig로 캐스팅해야 값을 읽고 쓸 수 있고, 손으로 만든 IServerConfig 구현체는 이 값들 대신 기본값을 씁니다.

5. UDP 지원

UDP 세션도 TCP와 같은 AppSession/IReceiveFilter 파이프라인을 씁니다. 다만 UDP에는 연결이 없으므로 "이 데이터그램이 누구 것인지"를 스스로 정해야 하고, 두 방식이 있습니다.

  • 원격 엔드포인트로 키를 삼는다 (기본) — 요청 타입이 UdpRequestInfo를 상속하지 않으면 이 방식입니다.
  • 페이로드에 담은 세션 ID로 키를 삼는다 — 요청 타입이 UdpRequestInfo를 상속하면, 클라이언트가 NAT 재바인딩을 겪어도 같은 논리적 세션을 유지할 수 있습니다.

예제는 Tutorials/SimpleUDPServer에 있습니다. UDP 관련 주의사항은 7.8절을 보세요.

6. 관측(Observability)

모든 지표는 Meter("SuperSocketLite") 하나로 나갑니다 — System.Diagnostics.Metrics 기반이라 OpenTelemetry 호환 수집기라면 무엇이든 붙일 수 있습니다.

종류이름비고
카운터 total-requests, total-bytes-received, total-bytes-sent, sessions-rejected, send-queue-full, send-errors, active-connections(UpDownCounter) 이벤트가 일어날 때마다 갱신 — 수집기가 없어도 Add 한 번의 비용이 든다
히스토그램 request-duration 요청 핸들러 안에서 보낸 시간
게이지 session-count 외 송신 큐 깊이·SocketAsyncEventArgs 풀 사용량(내부용, C# 공개 속성은 아님) ObservableGauge — 수집기가 실제로 물어볼 때만 계산되어 아무도 안 보면 비용이 0

7. 꼭 알아야 할 것

아래 8가지는 컴파일은 되지만 부하가 걸려야 드러나는 종류의 문제들입니다. 원문은 .claude/cautions.md에 있고, 이 절은 그것을 그대로 옮긴 것입니다.

7.1 스레드 안전성

NewSessionConnected와 NewRequestReceived는 서로 다른 스레드에서 동시에 호출될 수 있습니다. 클라이언트가 접속 직후 바로 패킷을 보내면 "connected 핸들러가 세션 상태를 아직 다 만들기 전에 첫 요청이 먼저 들어오는" 레이스가 생길 수 있습니다.

ServerConfig.SyncSessionConnectedEvent = true로 두면 NewSessionConnected가 accept 경로에서 동기 호출되어 "connected → 첫 요청" 순서가 구조적으로 보장됩니다. 대신 이 핸들러가 accept 자체를 블로킹하므로 반드시 가볍게 유지해야 합니다. (기본값은 false = 기존 동작)

7.2 송신 버퍼 수명 (zero-copy)

Send(byte[], int, int) / Send(ArraySegment<byte>) / Send(IList<ArraySegment<byte>>) / SendAsync(ReadOnlyMemory<byte>)(배열 기반일 때)는 호출자의 배열을 참조로 큐에 넣습니다. 전송이 완료되기 전에 그 배열을 수정하면 잘못된 데이터가 나갑니다. 

// 위험: buffer를 재사용하는 코드
session.Send(buffer, 0, len);
buffer[0] = 0;          // 아직 전송 중일 수 있다

// 안전: 세션이 풀 버퍼로 복사해 간다
session.SendCopied(buffer.AsSpan(0, len));
buffer[0] = 0;          // OK

Send(IList<...>)의 리스트 자체는 enqueue 시 복사되므로 호출 직후 재사용해도 됩니다 (배열만 공유됩니다).

빈 데이터 처리가 다릅니다. TrySendCopied/SendCopied는 데이터가 비면 아무것도 큐에 넣지 않고 성공으로 돌아갑니다. 반면 Send(buffer, 0, 0)은 길이 0 세그먼트를 큐에 넣어 실제로 전송을 시도합니다 — UDP에서는 빈 데이터그램이 나갑니다. 빈 패킷에 의미가 있는 프로토콜을 Send에서 SendCopied로 옮길 때만 확인하면 됩니다.

7.3 수신 필터

필터는 파이프에서 ReadOnlySequence<byte>를 직접 받습니다. 요청이 아직 완성되지 않았으면 consumed를 전진시키지 말고 그대로 두면 됩니다 — 데이터는 파이프에 남고 다음 수신 때 이어서 옵니다. 필터가 자체 캐리 버퍼를 두면 오히려 복사가 늘어납니다.

header/body는 세그먼트 여러 개에 걸쳐 있을 수 있습니다. header.First.Span으로 바로 읽지 말고 CopyTo(Span)이나 ToArray()를 씁니다.

UDP + UdpRequestInfo 조합에서 세션 ID 파싱용 필터는 수신 스레드당 1개가 재사용됩니다 (Reset() 후 재사용). 이 필터는 데이터그램 간 상태를 갖지 않아야 하고, CreateFilter에 넘어온 원격 엔드포인트를 캡처해서는 안 됩니다.

7.4 RequestInfo와 본문의 수명

라이브러리는 NewRequestReceived 핸들러를 동기로 부르고, 핸들러가 전부 리턴한 뒤에야 파이프를 전진시킵니다. UDP도 같습니다 — 수신 버퍼는 핸들러 리턴 후에 풀로 돌아갑니다.

이 보장 덕분에 앱은 패킷당 할당을 0으로 만들 수 있습니다. 필터가 요청 인스턴스 하나를 돌려 쓰고 본문을 ReadOnlySequence<byte>로 그대로 넘기면 됩니다(Tutorials/EchoServer가 그 형태). 대신 계약이 생깁니다.

핸들러가 리턴하면 그 RequestInfo와 본문은 더 이상 유효하지 않습니다. 필드에 저장하거나, 람다에 캡처하거나, 다른 스레드 큐에 넣으면 안 됩니다. 값을 남기려면 핸들러 안에서 역직렬화하거나 복사하세요. 패킷을 로직 스레드로 넘기는 구조라면 이 방식을 쓸 수 없습니다 — 그때는 ArrayPool에서 빌려 복사하고 처리 후 한 곳에서만 반납합니다(Tutorials/PvPGameServer가 그 형태).

어겨도 컴파일은 되고 가벼운 부하에서는 대개 동작합니다. 파이프 버퍼가 재사용될 만큼 부하가 올라가야 데이터가 깨지므로 찾기 매우 어려운 버그가 됩니다.

이 계약의 그림과 두 갈래(동기 처리 vs 스레드 핸드오프)는 안내서 4장에, 실제로 잰 효과는 GC·데이터 복사 최소화 가이드에 있습니다.

7.5 시간 값은 UTC

AppSession.StartTime/LastActiveTime, AppServerBase.StartedTime은 UTC입니다. 화면·로그에 로컬 시간으로 찍으려면 .ToLocalTime()을 붙이세요. LastActiveTime은 단조 tick에서 역산하므로 수 ms 오차가 있습니다.

7.6 타임아웃 처리 순서

TimeoutException 발생 후 세션을 종료할 때 반드시 아래 순서를 지킵니다.

// 올바른 순서
session.SendEndWhenSendingTimeOut();
session.Close();
SendEndWhenSendingTimeOut() 없이 Close()만 호출하면 InSending 플래그가 풀리지 않아 그 세션은 영영 정리되지 않습니다.

7.7 최대 연결 수 초과

MaxConnectionNumber 초과 시 SuperSocketLite가 즉시 연결을 끊습니다. 이 경우 NewSessionConnected가 호출되지 않습니다.

7.8 UDP 모드

UDP 세션은 내부 소켓 인스턴스가 세션 간에 공유되는 구조라 TryValidateClosedBySocket류 판정이 TCP와 다르게 동작합니다. Close() 내부에서 UDP/TCP 경로가 분기되므로 UDP 관련 코드를 수정할 때는 주의하세요.
