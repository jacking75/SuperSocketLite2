1. 라이브러리는 무엇을 대신해 주나

소켓 서버를 직접 짜면 늘 같은 문제를 다시 풉니다. 비동기 accept 루프, SocketAsyncEventArgs 재사용, TCP는 스트림이라 패킷 경계가 없다는 사실, 여러 스레드가 같은 세션에 동시에 쓰려 할 때의 경합, 종료 중에 보내던 데이터가 잘리는 문제. SuperSocketLite는 이 다섯 가지를 대신 처리합니다.

여러분이 채우는 곳은 두 군데뿐입니다.

1. 수신 필터

바이트 스트림에서 "여기까지가 패킷 하나"를 정하는 규칙. IReceiveFilter를 상속해 만듭니다.

2. 요청 핸들러

패킷 하나를 받았을 때 할 일. NewRequestReceived 이벤트에 붙입니다.

가장 작은 서버

4바이트 길이 프리픽스 뒤에 본문이 오는 프로토콜을 그대로 되돌려 보내는 서버입니다.

// 요청 하나를 나타내는 타입.
// Body는 수신 파이프의 메모리를 그대로 가리키고, 필터가 인스턴스를 돌려 쓴다.
public sealed class MyRequestInfo : IRequestInfo
{
    public string Key => string.Empty;
    public ReadOnlySequence<byte> Body { get; private set; }
    public void Set(ReadOnlySequence<byte> body) => Body = body;
}

// 4바이트 길이 프리픽스를 읽고 본문 크기를 알려 준다.
public sealed class MyReceiveFilter : FixedHeaderReceiveFilter<MyRequestInfo>
{
    private readonly MyRequestInfo _reusable = new();

    public MyReceiveFilter() : base(4) { }

    protected override int GetBodyLengthFromHeader(ReadOnlySequence<byte> header)
    {
        Span<byte> buf = stackalloc byte[4];
        header.CopyTo(buf);                       // 헤더가 조각에 걸쳐 있어도 안전하다
        return BinaryPrimitives.ReadInt32LittleEndian(buf);
    }

    protected override MyRequestInfo ResolveRequestInfo(
        ReadOnlySequence<byte> header, ReadOnlySequence<byte> body)
    {
        _reusable.Set(body);
        return _reusable;
    }
}

public sealed class MySession : AppSession<MySession, MyRequestInfo> { }

public sealed class MyServer : AppServer<MySession, MyRequestInfo>
{
    public MyServer() : base(new DefaultReceiveFilterFactory<MyReceiveFilter, MyRequestInfo>()) { }
}

띄우는 코드는 이렇게 짧습니다.

var config = new ServerConfig
{
    Ip = "Any", Port = 2012, MaxConnectionNumber = 1000,
    Mode = SocketMode.Tcp, Name = "EchoServer"
};

var server = new MyServer();
server.NewRequestReceived += (session, request) =>
{
    if (request.Body.IsSingleSegment)
        session.SendCopied(request.Body.FirstSpan);
    else
        session.SendCopied(request.Body.ToArray());   // 드묾: 패킷이 파이프 조각에 걸친 경우
};

server.Setup(new RootConfig(), config, logFactory: new ConsoleLogFactory());
server.Start();
여기서 이미 중요한 선택이 하나 끝났습니다. 위 핸들러는 받은 자리에서 바로 응답하고 끝납니다. 그래서 요청 객체를 돌려 쓰고 본문을 복사하지 않아도 됩니다. 패킷을 다른 스레드로 넘기는 서버라면 이야기가 달라집니다 — 4장에서 자세히 봅니다.

계층은 이렇게 쌓여 있습니다

자세한 관계는 전체 구조도에서 확대·검색하며 볼 수 있습니다.

2. 받는 쪽 — 바이트가 요청이 되기까지

TCP는 스트림입니다. 클라이언트가 패킷 하나를 보내도 서버가 그것을 한 번에 받는다는 보장이 없고, 반대로 세 개가 한 번에 붙어 올 수도 있습니다. 그래서 "지금까지 받은 바이트에서 완성된 패킷을 잘라내는" 일이 필요한데, 그게 수신 필터입니다.

라이브러리 쪽 흐름은 이렇습니다. 점이 데이터라고 생각하고 따라가 보세요.

필터가 하는 일은 두 가지입니다

FixedHeaderReceiveFilter<T>를 쓰면 딱 두 메서드만 채우면 됩니다.

메서드답해야 하는 질문
GetBodyLengthFromHeader(header) 헤더를 봤다. 본문은 몇 바이트 더 와야 하나?
ResolveRequestInfo(header, body) 다 왔다. 이걸 무슨 요청 객체로 만들까?

길이가 모자라면 아무것도 하지 않아도 됩니다. 라이브러리가 알아서 "아직"이라고 판단하고 데이터를 파이프에 남겨 둡니다. 직접 버퍼를 이어 붙이거나 오프셋을 계산할 일이 없습니다.

header와 body는 여러 조각에 걸쳐 있을 수 있습니다. header.First.Span으로 바로 읽지 말고 CopyTo(Span)을 쓰세요. 위 예제가 stackalloc에 복사해서 읽는 이유가 이것입니다.

더 자세한 단계별 흐름은 수신 흐름 다이어그램에 있습니다.

3. 보내는 쪽 — 응답이 소켓으로 나가기까지

보내는 쪽에서 라이브러리가 해결해 주는 것은 "같은 세션에 여러 스레드가 동시에 쓰면 어떻게 되나"입니다. 답은 간단합니다. 아무나 큐에 넣을 수 있지만, 실제로 소켓에 쓰는 것은 언제나 한 줄기뿐입니다.

어떤 Send를 쓸까

상황API왜
보통의 단발 응답 SendCopied(span) 라이브러리 풀 버퍼로 복사해 넣는다. 내 버퍼를 곧바로 다시 써도 된다.
같은 내용을 여러 명에게 Send(byte[], 0, len) 복사하지 않고 배열을 공유한다. 대신 보낸 뒤 그 배열을 고치면 안 된다.
느린 클라이언트, 기다려도 됨 SendAsync(memory, ct) 큐가 찼을 때 스핀 대신 비동기로 기다린다. 타임아웃은 취소 토큰으로 건다.
큐가 차면 그냥 포기 TrySendCopied(span) false를 돌려준다. 예외를 던지지 않는다.
타임아웃 뒤 처리 순서가 정해져 있습니다. TimeoutException을 잡고 세션을 끊을 거라면 반드시 session.SendEndWhenSendingTimeOut()을 먼저 부르고 Close()를 부르세요. 이 호출이 InSending 플래그를 풀어 줍니다. 건너뛰면 그 세션은 영영 닫히지 않습니다.

단계별 흐름은 송신 흐름 다이어그램에 있습니다.

4. 꼭 지켜야 할 계약 하나

이 라이브러리에서 성능과 안전성을 동시에 가르는 결정은 딱 하나입니다. 패킷을 핸들러 안에서 다 처리하는가, 아니면 다른 스레드로 넘기는가.

왼쪽을 고를 수 있는 이유

라이브러리는 핸들러를 동기로 부르고, 핸들러가 전부 리턴한 뒤에야 파이프를 전진시킵니다. 그래서 핸들러가 도는 동안에는 본문 메모리가 확실히 살아 있습니다. 필터도 세션마다 하나이고, 같은 세션의 다음 패킷은 이번 핸들러가 끝난 뒤에 파싱됩니다.

그래서 생기는 제약: 핸들러가 리턴하면 그 요청 객체와 본문은 더 이상 유효하지 않습니다. 필드에 저장하거나, 람다에 캡처하거나, 다른 스레드 큐에 넣으면 안 됩니다.

어겨도 컴파일은 되고, 가벼운 부하에서는 대개 잘 돕니다. 파이프 버퍼가 재사용될 만큼 부하가 올라가야 데이터가 깨지므로 찾기 매우 어려운 버그가 됩니다. 값을 남겨야 하면 핸들러 안에서 역직렬화하거나 복사하세요.

오른쪽을 고를 때

패킷을 로직 스레드로 넘긴다면 본문 복사는 피할 수 없습니다. 다만 new byte[] 대신 ArrayPool<byte>.Shared에서 빌리면 할당은 없앨 수 있습니다. 이때 규칙은 하나입니다 — 반납 지점을 한 곳으로 정하고 거기서만 반납하는 것. Tutorials/PvPGameServer가 이 형태이며, 반납은 PacketProcessor.Process()의 finally 한 곳에서만 합니다.

두 방식의 자세한 근거와 실제로 측정한 효과는 GC·데이터 복사 최소화 가이드에 있습니다.

기초 — 에코 서버 계열

모두 핸들러에서 바로 응답하고 끝납니다. 요청 인스턴스를 돌려 쓰는 형태로 작성되어 있습니다.

EchoServer 동기 처리

가장 먼저 볼 것 · 5바이트 헤더(전체 길이 2 + 패킷 ID 2 + 예약 1)

받은 것을 그대로 돌려보내는 최소 구성입니다. ReceiveFilter.cs에 요청 타입과 필터가 함께 있고, MainServer.cs에 서버 설정과 핸들러가 있습니다. 파일 세 개가 전부라서 라이브러리를 쓰는 데 최소한 무엇이 필요한지 한눈에 보입니다.

  • 응답을 만들 때 stackalloc 버퍼에 직렬화하고 SendCopied로 보냅니다.
  • 필터가 요청 인스턴스 하나를 돌려 씁니다 — 패킷을 받는 데 드는 할당이 없습니다.

실행: 빌드 후 Tutorials/00_server_bins/run_EchoServer.bat · 클라이언트는 EchoClient

EchoServerEx 동기 처리

EchoServer + 실행 인자 + 로깅

같은 에코 서버에 실무에서 필요한 두 가지를 붙였습니다. 포트·최대 접속 수 같은 설정을 명령행 인자로 받고 (CommandLineParser), 로그를 NLog로 내보냅니다. 그리고 패킷 ID로 핸들러를 찾아 부르는 디스패치 맵이 처음 등장합니다 — 패킷 종류가 늘어나면 필요한 구조입니다.

실행: run_EchoServerEx.bat

EchoServer_GenericHost 동기 처리

.NET Generic Host 위에서 서비스로 띄우기

서버를 IHostedService로 감싸 Generic Host가 수명을 관리하게 합니다. 설정은 appsettings.json에서 읽고, 로깅·DI도 호스트 것을 씁니다. 실제 배포에서 흔히 쓰는 형태라, 사내 표준이 Generic Host라면 여기부터 보면 됩니다.

프로토콜과 포트

BinaryPacketServer 동기 처리

패킷 경계를 직접 설계해 보는 예제 · 요청 헤더 12바이트

헤더에 패킷 ID(4바이트)와 값 두 개, 본문 길이(4바이트)가 들어 있는 구조입니다. GetBodyLengthFromHeader가 헤더의 특정 위치에서 길이를 읽어 오는 모습을 보여 줍니다.

이 예제는 요청 헤더(12바이트)와 응답 헤더(8바이트)의 형식이 다릅니다. 의도된 것이니 코드를 읽을 때 헷갈리지 마세요.

MultiPortServer 동기 처리

한 프로세스가 포트를 여러 개 여는 방법

서버 인스턴스를 두 개 만들어 각각 다른 포트로 Start()합니다. 내부 서버용 포트와 외부 클라이언트용 포트를 분리하고 싶을 때 쓰는 형태입니다. 포트마다 다른 프로토콜을 쓰고 싶다면 필터와 요청 타입도 따로 두면 됩니다.

SimpleUDPServer 동기 처리

연결이 없는 UDP에서 세션을 무엇으로 찾을 것인가

UDP에는 연결이 없으므로 "이 데이터그램이 누구 것인지"를 스스로 정해야 합니다. 이 예제는 요청 타입이 UdpRequestInfo를 상속해서, 페이로드에 직접 담은 세션 ID로 세션을 찾는 방식을 씁니다. 그렇게 하면 클라이언트가 NAT 재바인딩을 겪어도 같은 논리적 세션을 유지합니다. 상속하지 않으면 원격 엔드포인트를 키로 씁니다.

이 예제는 수신 핸들러를 등록하지 않은 최소 골격입니다. 필터가 데이터그램을 어떻게 해석하는지 보는 용도이지, 그대로 돌려서 에코를 기대하면 안 됩니다.

sendFailTestServer 동기 처리

받지 않는 클라이언트에 계속 보내면 무슨 일이 생기나

SendTimeOut, SendingQueueSize, SendBufferSize를 작게 잡고 타이머로 계속 패킷을 밀어 넣어 TimeoutException을 일부러 재현합니다. 운영에서 만나기 전에 한 번은 봐 둘 만한 예제입니다.

핵심은 예외를 잡은 뒤의 순서입니다. 

catch (TimeoutException ex)
{
    // 이 호출이 InSending 플래그를 풀어 준다. 건너뛰면 세션이 닫히지 않는다.
    session.SendEndWhenSendingTimeOut();
    session.Close();
}

게임 서버 구조 — 로직 스레드로 넘기는 예제

여기부터는 수신 스레드에서 게임 로직을 돌리지 않습니다. 패킷을 큐에 넣고 별도 스레드가 꺼내 처리합니다. 그래서 본문을 복사해야 합니다.

ChatServer 스레드 핸드오프

가장 단순한 핸드오프 · 로직 스레드 1개

수신 핸들러는 패킷을 ServerPacketData에 옮겨 담아 BufferBlock 큐에 넣고 곧바로 돌아갑니다. PacketProcessor의 스레드 하나가 그 큐를 비우며 로그인·방 입장·채팅을 처리합니다. 로직이 한 스레드에서만 돌기 때문에 방·유저 자료구조에 락이 필요 없습니다 — 이 예제의 핵심입니다.

브로드캐스트는 Room.cs에 있습니다. 패킷 배열을 하나만 만들어 방 안 모든 세션에 같은 배열을 넘깁니다. 사람 수만큼 복사하지 않습니다.

ChatServerEx 스레드 핸드오프

ChatServer + 로직 스레드 여러 개 + DB 워커

ChatServer와 기능은 같지만 처리 구조가 다릅니다. 방을 스레드별로 나눠 배정해서 스레드마다 자기 방만 건드리게 합니다. 락 없이 병렬성을 얻는 흔한 방법입니다. PacketDistribute가 패킷을 어느 프로세서로 보낼지 정합니다.

DB 접근은 또 한 번 넘깁니다. DB 워커 스레드가 처리한 뒤 결과를 다시 패킷으로 만들어 공용 큐에 넣습니다. 2단 핸드오프인 셈이라, 로직 스레드가 DB 응답을 기다리며 멈추지 않습니다.

PvPGameServer 스레드 핸드오프

MemoryPack 직렬화 · 룸 기반 대전 · ArrayPool 적용 예

직렬화를 MemoryPack으로 하고, 요청 객체를 통째로 로직 스레드 큐에 넣습니다. 저장소 안에서 버퍼 풀링을 실제로 적용한 예제이기도 합니다 — 수신 필터가 ArrayPool에서 빌리고, PacketProcessor.Process()의 finally 한 곳에서 반납합니다.

풀에서 빌린 배열은 요청한 크기보다 클 수 있습니다. 그래서 길이는 Data.Length가 아니라 DataSize로 들고 다니고, 역직렬화에는 DataSpan을 넘깁니다. 풀링을 흉내 낼 때 가장 흔히 놓치는 지점입니다.

GameServer_MoDedicated / MoDedicated2 스레드 핸드오프

전용(dedicated) 게임 서버 모양

구조는 ChatServer와 같습니다(큐 + 로직 스레드). 차이는 게임 업데이트 루프가 따로 있다는 점입니다. MoDedicated2는 업데이트 스레드를 여러 개(기본 4개) 두고 방을 나눠 맡깁니다. 패킷 처리와 게임 틱을 어떻게 나눌지 고민할 때 참고할 만합니다.

GateServer_GameServer 스레드 핸드오프

앞단 게이트 서버가 받아 뒤로 넘기는 구조

클라이언트는 게이트에만 붙고, 게이트가 뒤쪽 게임 서버로 패킷을 넘깁니다. 접속 수와 인증을 앞단에서 흡수하고 게임 서버는 로직에 집중하게 하는 배치입니다. CommonLib에 두 서버가 공유하는 패킷 정의가 있습니다.

이 예제는 골격 위주입니다. 패킷 핸들러 등록이 비어 있어서 받은 패킷을 로그로만 남깁니다. 구조를 보는 용도로 읽으세요.

클라이언트 예제

서버를 시험하려면 짝이 되는 클라이언트가 필요합니다. EchoClient(WinForms)는 에코 계열 서버 대부분에 쓸 수 있고, ChatClient(WPF)는 채팅 서버용, PvPGameServer_Client는 PvP 서버용입니다. 셋 다 패킷 조립 버퍼(PacketBufferManager)를 직접 구현하고 있어, 클라이언트 쪽에서 TCP 스트림을 어떻게 잘라 쓰는지도 함께 볼 수 있습니다.
