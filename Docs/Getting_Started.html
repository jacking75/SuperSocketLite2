1. Building

Requirements

  • .NET 10.0 SDK
  • Windows or Linux — both the async socket engine (SocketAsyncEventArgs/IOCP) and the TCP keep-alive options are cross-platform.

Building just the library

cd SuperSocketLite
dotnet build -c Release

The output lands in bin/net10.0/ at the repository root — SuperSocketLite.csproj sets OutputPath to ..\bin (one level up from the csproj).

The package version in the current source (per SuperSocketLite.csproj) is 0.21.0. Building the whole solution (SuperSocketLite2.slnx) writes the example executables into the run folders (Tutorials/*/00_server_bins, Tutorials/00_client_bin, Template/00_server_bins, etc.). Those folders are git-ignored — only the hand-written run_*.bat launch scripts are committed — so a full build leaves no binary diffs in the repository.

Referencing it — a separate NuGet package, SuperSocketLite2

This repository's code (receive built on System.IO.Pipelines, send built on Channel<T>) ships as its own NuGet package, SuperSocketLite2 — a different package ID from the older SuperSocketLite package on NuGet.org (still the pre-rewrite, .NET 9 line, unaffected by this repository). 

dotnet add package SuperSocketLite2

That's it — no local checkout needed. Tutorials/EchoServer_NuGet is a complete, runnable server built entirely against the package (identical to Tutorials/EchoServer, just with a PackageReference instead of a ProjectReference).

If you want the latest source instead of a released version — unreleased fixes, or modifying the library itself — reference the project directly instead.

git clone https://github.com/jacking75/SuperSocketLite2.git
<ItemGroup>
  <ProjectReference Include="..\SuperSocketLite2\SuperSocketLite\SuperSocketLite.csproj" />
</ItemGroup>

Verifying with the tests

The repo ships both a regression suite that verifies the library itself and a load-test toolkit that drives real TCP/UDP traffic against a live server to measure throughput and latency. Neither is xUnit — both are custom runners. 

dotnet run --project Test/SuperSocketLiteRegressionTests -c Release
dotnet run --project Test/LoadTest/SuperSocketLite.LoadTest.Tests -c Release

For exact case counts and coverage, see the "Testing & Quality" section of the repository root's README.md.

2. Building a Minimal Server

There are exactly two things you fill in: a receive filter that decides where packet boundaries fall, and a request handler for what to do with a packet once you have one. Below is a minimal server that echoes back a protocol consisting of a 4-byte length prefix followed by a body — it builds and runs as-is. 

// EchoProtocol.cs
using System.Buffers;
using System.Buffers.Binary;
using SuperSocketLite.SocketBase;
using SuperSocketLite.SocketBase.Protocol;
using SuperSocketLite.SocketEngine.Protocol;

// The request info. Body points straight at the receive pipe's memory, and the filter
// hands back the same instance every time, so receiving a packet allocates nothing.
// Once the handler returns, though, this instance and Body are no longer valid (see 7.4).
public sealed class MyRequestInfo : IRequestInfo
{
    public string Key => string.Empty;
    public ReadOnlySequence<byte> Body { get; private set; }
    public void Set(ReadOnlySequence<byte> body) => Body = body;
}

// Reads the 4-byte length prefix and reports how big the body is.
public sealed class MyReceiveFilter : FixedHeaderReceiveFilter<MyRequestInfo>
{
    private readonly MyRequestInfo _reusable = new();

    public MyReceiveFilter() : base(4) { }

    protected override int GetBodyLengthFromHeader(ReadOnlySequence<byte> header)
    {
        Span<byte> buffer = stackalloc byte[4];
        header.CopyTo(buffer);                       // safe even if the header spans segments
        return BinaryPrimitives.ReadInt32LittleEndian(buffer);
    }

    protected override MyRequestInfo ResolveRequestInfo(
        ReadOnlySequence<byte> header, ReadOnlySequence<byte> body)
    {
        _reusable.Set(body);
        return _reusable;
    }
}

public sealed class MySession : AppSession<MySession, MyRequestInfo> { }

public sealed class MyServer : AppServer<MySession, MyRequestInfo>
{
    public MyServer() : base(new DefaultReceiveFilterFactory<MyReceiveFilter, MyRequestInfo>()) { }
}
// Program.cs
using SuperSocketLite.SocketBase;
using SuperSocketLite.SocketBase.Config;
using SuperSocketLite.SocketBase.Logging;

var config = new ServerConfig
{
    Ip = "Any",
    Port = 2012,
    MaxConnectionNumber = 1000,
    Mode = SocketMode.Tcp,
    Name = "EchoServer"
};

var server = new MyServer();

server.NewRequestReceived += (session, request) =>
{
    if (request.Body.IsSingleSegment)
        session.SendCopied(request.Body.FirstSpan);
    else
        session.SendCopied(request.Body.ToArray());   // rare: the packet spans pipe segments
};

if (!server.Setup(new RootConfig(), config, logFactory: new ConsoleLogFactory()))
{
    Console.WriteLine("Failed to set up the server.");
    return;
}

server.Start();
Console.WriteLine("Listening on 2012. Press any key to stop...");
Console.ReadKey();
server.Stop();
A ready-to-run project version of this lives at Tutorials/EchoServer. The layered structure and animated receive/send flow are in chapters 1–3 of the Guide; which tutorial to read next is in Reading Order for the Examples.

3. Which Send to Use — the Send API

The four send APIs differ in whether they copy and what happens when the queue is full. Pick the one that fits.

MethodCopy semanticsWhen to use it
Send(byte[], offset, length) / TrySend Zero-copy — the library keeps a reference to your array You own a buffer you won't touch again until it's sent
SendCopied(ReadOnlySpan<byte>) / TrySendCopied Copies into a pooled buffer You need your buffer back immediately (e.g. a reused scratch buffer)
SendAsync(ReadOnlyMemory<byte>, CancellationToken) Zero-copy for array-backed memory You want to await when the send queue is full instead of spinning. SendTimeOut doesn't apply; cancel via the token
Send(IList<ArraySegment<byte>>) The list is copied on enqueue (the arrays are not) Sending several segments as one logical message — the list can be reused right after the call
TrySend/TrySendCopied return false without throwing when the session is closed or the queue is full. Send/SendCopied, on the other hand, wait up to ServerConfig.SendTimeOut and then throw TimeoutException — see section 7.6 for the exact order of operations after you catch it.

4. Key Settings

ServerConfig covers the usual suspects (Port, MaxConnectionNumber, ReceiveBufferSize, SendTimeOut, TCP keep-alive, idle session cleanup) plus a few knobs worth knowing about.

SettingDefaultWhat it's for
ReceiveInlineOnIocpThread true Advances the receive pipe directly on the IOCP completion thread instead of dispatching to the thread pool — saves a thread hop and two Task allocations per received packet.
PreAllocateSAEA / MinPoolSize true / 100 Pre-allocate every pooled SocketAsyncEventArgs at startup for the best accept-time latency, or grow the pool on demand from MinPoolSize.
MaxReceivePipeBufferSize 65536 The receive pipe's backpressure threshold; automatically raised to fit MaxRequestLength.
SyncSessionConnectedEvent false Raises NewSessionConnected synchronously during accept, structurally guaranteeing it runs before a fast client's first request. Keep the handler light — it now blocks accept.
AcceptLoopCount 1 Runs several concurrent accept loops on the same listening socket — helps absorb a reconnect storm.
UseZeroByteReceive false An idle session waits on a zero-byte receive instead of holding a real receive buffer — cuts idle-connection memory on servers where most sessions are quiet.
KeepAliveRetryCount 5 How many unacknowledged keep-alive probes go out before the connection is treated as dead. 0 or less leaves the OS default alone.
The four settings above (ReceiveInlineOnIocpThread, SyncSessionConnectedEvent, MaxReceivePipeBufferSize, KeepAliveRetryCount) live only on the ServerConfig class, not on the IServerConfig interface. If you're holding the config through an interface-typed variable, cast with config as ServerConfig to read or set them — a hand-written IServerConfig implementation gets the defaults instead.

5. UDP Support

UDP sessions go through the same AppSession/IReceiveFilter pipeline as TCP. UDP has no connection, though, so something has to decide "whose datagram is this" — there are two ways.

  • Keyed by remote endpoint (default) — used whenever your request type doesn't inherit from UdpRequestInfo.
  • Keyed by a session ID embedded in the payload — used when your request type inherits from UdpRequestInfo, so a client keeps the same logical session across a NAT rebind.

An example lives at Tutorials/SimpleUDPServer. UDP-specific caveats are in section 7.8.

6. Observability

Everything is published through a single Meter("SuperSocketLite") — built on System.Diagnostics.Metrics, so any OpenTelemetry-compatible collector can attach.

KindNameNotes
Counters total-requests, total-bytes-received, total-bytes-sent, sessions-rejected, send-queue-full, send-errors, active-connections (an UpDownCounter) Updated as events happen — costs one Add even with nobody listening
Histogram request-duration Time spent inside your request handler
Gauges session-count, plus internal send-queue-depth and SocketAsyncEventArgs pool-usage gauges (not public C# properties) ObservableGauges — computed only when a collector actually asks, so the cost is zero when nobody is watching

7. Must-Knows

The 8 items below compile fine and mostly work at light load — the kind of problem that only shows up under real traffic. The same 8 items stand on their own at Known Caveats — if you change one, change the other.

7.1 Thread safety

NewSessionConnected and NewRequestReceived can be called concurrently on different threads. If a client sends a packet immediately after connecting, you can hit a race where the first request arrives before the connected handler has finished setting up session state.

Set ServerConfig.SyncSessionConnectedEvent = true and NewSessionConnected is called synchronously in the accept path, structurally guaranteeing the "connected → first request" order. In exchange, that handler now blocks accept, so keep it light. (Default is false — the original behavior.)

7.2 Send buffer lifetime (zero-copy)

Send(byte[], int, int) / Send(ArraySegment<byte>) / Send(IList<ArraySegment<byte>>) / SendAsync(ReadOnlyMemory<byte>) (when array-backed) enqueue a reference to your array. Modify that array before the send completes and corrupted data goes out on the wire. 

// Dangerous: reusing buffer
session.Send(buffer, 0, len);
buffer[0] = 0;          // may still be in flight

// Safe: the session copies into a pooled buffer
session.SendCopied(buffer.AsSpan(0, len));
buffer[0] = 0;          // OK

For Send(IList<...>), the list itself is copied on enqueue, so it's safe to reuse right after the call (only the arrays it references are shared).

Empty data is handled differently. TrySendCopied/SendCopied enqueue nothing and return success when given empty data. Send(buffer, 0, 0), by contrast, enqueues a zero-length segment and actually attempts to send it — on UDP that means an empty datagram goes out. Only relevant if you're moving a protocol where an empty packet is meaningful from Send to SendCopied.

7.3 Receive filters

Your filter receives a ReadOnlySequence<byte> straight from the pipe. If a request isn't complete yet, just leave consumed where it is — the data stays in the pipe and continues on the next receive. A filter with its own carry buffer only adds copies back in.

header/body can span multiple segments. Don't read header.First.Span directly — use CopyTo(Span) or ToArray().

For UDP combined with UdpRequestInfo, the filter that parses the session ID is reused once per receive thread (via Reset()). It must not carry state between datagrams, and it must not capture the remote endpoint passed into CreateFilter.

7.4 RequestInfo and body lifetime

The library calls your NewRequestReceived handler synchronously, and only advances the pipe after the handler fully returns. UDP is the same — the receive buffer goes back to the pool after the handler returns.

That guarantee is what lets an app get to zero allocations per packet: the filter reuses one request instance and hands the body across as a ReadOnlySequence<byte> (Tutorials/EchoServer is built this way). In exchange, a contract applies.

Once the handler returns, that RequestInfo and its body are no longer valid. Don't store them in a field, capture them in a lambda, or push them onto another thread's queue. Deserialize or copy inside the handler if you need to keep the value. If your architecture hands packets off to a logic thread, this approach doesn't apply — borrow from ArrayPool instead, copy, and return it in exactly one place after processing (Tutorials/PvPGameServer is built this way).

Violate this and it still compiles, and usually still works under light load. Data only corrupts once load is high enough for the pipe's buffer to get reused, which makes this a very hard bug to find.

The diagram for this contract and its two branches (synchronous handling vs. thread handoff) is in Guide chapter 4; measured effects are in the GC and Copy Minimization guide (Korean).

7.5 Time values are UTC

AppSession.StartTime/LastActiveTime and AppServerBase.StartedTime are UTC. Call .ToLocalTime() before displaying them locally. LastActiveTime is derived from a monotonic tick count, so it can be off by a few milliseconds.

7.6 Order of operations after a timeout

After a TimeoutException, closing the session requires this exact order.

// Correct order
session.SendEndWhenSendingTimeOut();
session.Close();
Calling Close() without SendEndWhenSendingTimeOut() first leaves the InSending flag set, and that session is never cleaned up.

7.7 Exceeding the maximum connection count

When MaxConnectionNumber is exceeded, SuperSocketLite drops the connection immediately, and NewSessionConnected is never called for it.

7.8 UDP mode

UDP sessions share an underlying socket instance across sessions, so close-detection behaves differently than on TCP. Close() branches internally between the UDP and TCP paths — be careful when touching UDP-related code.
