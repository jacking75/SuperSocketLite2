SuperSocketLite Architecture

What each part does from the listener down to your handler, what order the receive, send and UDP paths run in, and what was deliberately left out.

1. Layer structure

[client TCP connection]
        ↓
[TcpAsyncSocketListener]       accept loop
        ↓
[AsyncSocketServer]            SocketAsyncEventArgs pool management, session creation
        ↓
[SocketSession]                state machine (InSending / InReceiving / Closed)
        ↓                      receive side uses System.IO.Pipelines
[AppSession<TSession, TReq>]   application-level session
        ↓
[IReceiveFilter<TRequestInfo>] byte stream → packet parsing
        ↓
[AppServerBase.ExecuteCommand] raises NewRequestReceived

2. Core components

Receive pipe SocketSession.cs

Each session owns one System.IO.Pipelines.Pipe. The IOCP completion thread only advances the PipeWriter; a ProcessPipeAsync() task reads from the PipeReader and hands the data to AppSession.ProcessRequest(ReadOnlySequence<byte>). The back-pressure threshold is tuned with ServerConfig.MaxReceivePipeBufferSize.

SmartPool<T> Common/SmartPool.cs

A ConcurrentStack-based object pool. AsyncSocketServer creates two of them: one of SocketAsyncEventArgsProxy for receiving and one of SocketAsyncEventArgs for sending. With PreAllocateSAEA (default true) all MaxConnectionNumber instances are created at startup; with false the pool starts at MinPoolSize and doubles as needed.

ChannelSendingQueue Common/ChannelSendingQueue.cs

The per-session send queue. It is built on a bounded Channel<SendItem>, so there is no separate lock. Capacity counts send calls, not segments — a multi-segment send still takes one slot.

SocketState bit flags SocketSession.cs

Normal      = 0x00
InSending   = 0x01
InReceiving = 0x02
InClosing   = 0x10
Closed      = 0x01000000

State transitions are made atomically with Interlocked.CompareExchange.

3. Accept and receive startup

  1. The accept loop in TcpAsyncSocketListener takes the socket. ServerConfig.AcceptLoopCount (default 1, range 1–64) lets you run several loops; only the last loop raises OnStopped.
  2. AsyncSocketServer.ProcessNewClient() takes a receive proxy and a send SAEA from their respective pools. If either is unavailable the connection is rejected and NewSessionConnected is not raised. In other words, exceeding MaxConnectionNumber drops the connection silently, with no event.
  3. SocketSession.Initialize() creates the per-session send queue and receive Pipe. The pipe's back-pressure thresholds are adjusted as below — this prevents the case where a large MaxRequestLength is configured and the pipe stalls first, so the request can never complete. 
    pauseThreshold  = max(MaxReceivePipeBufferSize (default 65536), ReceiveBufferSize * 2)
if MaxRequestLength > 0
pauseThreshold  = max(pauseThreshold, MaxRequestLength + ReceiveBufferSize * 2)
resumeThreshold = pauseThreshold / 2
  4. AsyncSocketSession.Start() launches StartReceive() and the ProcessPipeAsync() task.
  5. StartReceive() is a while loop. It takes a buffer from _pipeWriter.GetMemory(), binds it with SetBuffer(Memory<byte>) and issues ReceiveAsync(). On synchronous completion it does not recurse — it goes around the loop once more, which keeps the stack from growing without bound on a socket that always has data ready (loopback, for instance). With UseZeroByteReceive=true an idle session waits on a zero-length buffer and only borrows a real buffer once there is something to read. Whether a completion is a probe is decided from the length of the posted buffer, so there is no state shared between threads.
  6. IOCP completion → ProcessReceiveCore() does Advance → FlushAsync → StartReceive() again. With ReceiveInlineOnIocpThread=true (the default) this advance runs on the IOCP thread itself. The app handler is not called inline — that belongs to the ProcessPipeAsync task.

4. Send path

AppSession.TrySend/Send → SocketSession.TrySend → ChannelSendingQueue.TryEnqueue
   → StartSend(true) → [only the caller that won the InSending flag proceeds]
   → DrainAvailable(_sendBatch, _pooledInFlight) → SendAsync/SendSync
   → completion → OnSendingCompleted → OnSendEnd if the queue is empty, else StartSend(false)
  • Queue: ChannelSendingQueue is a single bounded Channel<SendItem>. There is no lock; completion and capacity decisions are left to the channel's atomic write. SendItem is a readonly struct, so an enqueue causes no heap allocation. Capacity counts send requests, not segments — one multi-segment Send is one slot.
  • Single-flight: only one send is in progress per session at a time. Only the caller that acquired the InSending flag actually sends; the rest enqueue and return.
  • Batching: the drain target lists (_sendBatch, _pooledInFlight) are reused per session. Because sending is single-flight, the next drain only fills them after the previous batch has left the socket.
  • Scatter-gather: with two or more segments they go out in one call via SocketAsyncEventArgs.BufferList. They are not copied into a single buffer.
  • Partial sends: if fewer bytes went out than requested, TrimSegments() trims to the remaining range and re-sends.
  • Returning pooled buffers: ArrayPool arrays borrowed by TrySendCopied/SendCopied are returned by ReturnPooledSendBuffers() where the batch ends (OnSendingCompleted / OnSendError). If the session dies while a send is still in flight they are not returned and are left to the GC — better than handing the same buffer out twice.

5. UDP path

Unlike TCP there is no pipe and no connection. One datagram is one request.

  1. UdpSocketListener issues ReceiveFromAsync with a buffer borrowed from ArrayPool. What arrives is wrapped in a UdpReceivePacket and passed to OnNewClientAccepted.
  2. UdpSocketServer invokes the filter. If the request type derives from UdpRequestInfo, the session is looked up by the session ID inside it; otherwise the remote endpoint string is used as the key. If no session exists, one is created on the spot.
  3. _requestHandler.ExecuteCommand(...) is called synchronously, and then UdpReceivePacket.Dispose() in the finally returns the buffer to the pool. So the receive buffer's lifetime matches TCP — it is invalid once the handler returns.
Two things to watch
  • The filter used to parse the session ID is reused, one per receive thread ([ThreadStatic], reused after Reset()). It must not carry state between datagrams, and must not capture the remote endpoint passed to CreateFilter.
  • UdpSocketSession shares the listening socket, so its Client is null. That is also why TryValidateClosedBySocket always returns false.

7. Logging

The library does not depend on any particular logging library; it only uses its own ILog / ILogFactory abstraction.

How to wire it up (recommended) — MicrosoftLoggingLogFactory

Serilog, NLog, ZLogger and log4net all ship a Microsoft.Extensions.Logging provider, so the one built-in bridge covers all of them. You do not need to write a per-library adapter. 

// plain setup
Setup(new RootConfig(), config, logFactory: new MicrosoftLoggingLogFactory(loggerFactory));

// GenericHost
services.AddSingleton<ILogFactory>(
    sp => new MicrosoftLoggingLogFactory(sp.GetRequiredService<ILoggerFactory>()));

Writing your own adapter

Only 5 level flags (IsDebug/Info/Warn/Error/FatalEnabled) and 7 methods (5 plain-text ones plus Error/Fatal taking an exception) are required. Everything else has a default implementation.

MemberRequiredNotes
IsDebug/Info/Warn/Error/FatalEnabledYes
IsTraceEnabledNoDefaults to false — no Trace is emitted unless you opt in
Debug/Info/Warn/Error/Fatal(string)Yes
Trace(string)NoFolds into Debug by default
Error/Fatal(string, Exception)Yes
Trace/Debug/Info/Warn(string, Exception)NoMerged into text by default
Log(LogEventLevel, in LogSessionContext, string, Exception?)NoOverride this if you want structured logging

Structured logging — LogSessionContext

Session information is passed separately instead of being concatenated into the message string. It is a readonly struct (two references), so there is no heap allocation and no boxing at the call site. 

Logger.Log(LogEventLevel.Error, session.SessionLogContext, "Max request length exceeded");

For an adapter that does not override Log, the default implementation merges it into [sessionId/endpoint] message and forwards it to the plain-text methods. Either way no newline is inserted — so a line-based collector never splits one event in two.

Default interface members are only visible when calling through the interface type. The library always holds an ILog, so it is fine, but a test calling directly through the concrete class type will not compile.

Avoiding name collisions

ILogProvider (distinct from MEL's ILoggerProvider) and LogEventLevel (distinct from MEL's LogLevel).

8. Receive filters

There is exactly one path. The filter receives a ReadOnlySequence<byte> straight from the pipe and parses it, and data that is not yet a complete request is left in the pipe (consumed is not advanced). There is no per-session carry buffer and no offset arithmetic. 

public interface IReceiveFilter<TRequestInfo>
    where TRequestInfo : IRequestInfo
{
    TRequestInfo? Filter(ReadOnlySequence<byte> buffer, out SequencePosition consumed, out SequencePosition examined);
    IReceiveFilter<TRequestInfo>? NextReceiveFilter { get; }
    void Reset();
    FilterState State { get; }
}
ReturnconsumedexaminedMeaning
RequestInfoend of the requestsame as consumedOne request completed. The loop continues with the remaining bytes
nullbuffer.Startbuffer.EndNot enough data. Leave it until the pipe receives more

Setting State to FilterState.Error closes the session with CloseReason.ProtocolError.

The MaxRequestLength check uses the unconsumed length (sequence.Slice(consumed).Length). The pipe may hold several complete pipelined requests, so measuring the whole buffer length would be wrong.

9. Baseline implementation pattern

Decide this first: do you handle the packet entirely inside NewRequestReceived, or hand it off to a logic thread? The answer determines the shape of your request info.

StructureRequest infoReference implementation
Handled immediately in the handler Reused instance + Body as ReadOnlySequence<byte> (zero allocation) Tutorials/EchoServer
Passed to a logic thread Copied into an ArrayPool array, returned in one place after processing Tutorials/PvPGameServer

The code below is the first one (handled immediately). The full rationale and the second pattern are in Docs/GC_Copy_Minimization.md (Korean). 

// 1. ReceiveFilter (example with a fixed 12-byte header)
public class ReceiveFilter : FixedHeaderReceiveFilter<EFBinaryRequestInfo>
{
    // There is one filter per session and the next packet is only parsed after the previous
    // handler returned, so the request instance can be reused. But it must not escape the handler.
    private readonly EFBinaryRequestInfo _reusable = new();

    public ReceiveFilter() : base(12) { }

    protected override int GetBodyLengthFromHeader(ReadOnlySequence<byte> header)
    {
        Span<byte> buf = stackalloc byte[12];
        header.CopyTo(buf);                       // safe even across a segment boundary
        return BinaryPrimitives.ReadInt32LittleEndian(buf.Slice(8, 4));
    }

    protected override EFBinaryRequestInfo ResolveRequestInfo(
        ReadOnlySequence<byte> header, ReadOnlySequence<byte> body)
    {
        Span<byte> buf = stackalloc byte[12];
        header.CopyTo(buf);

        _reusable.Set(
            BinaryPrimitives.ReadInt32LittleEndian(buf.Slice(0, 4)),
            BinaryPrimitives.ReadInt16LittleEndian(buf.Slice(4, 2)),
            BinaryPrimitives.ReadInt16LittleEndian(buf.Slice(6, 2)),
            body);                                // points straight into the pipe, no copy

        return _reusable;
    }
}

// 2. AppServer
public class MainServer : AppServer<NetworkSession, EFBinaryRequestInfo>
{
    public MainServer()
        : base(new DefaultReceiveFilterFactory<ReceiveFilter, EFBinaryRequestInfo>()) { }

    protected override void OnStarted()
    {
        NewSessionConnected += OnConnected;
        SessionClosed += OnClosed;
        NewRequestReceived += OnPacketReceived;
    }
}

10. Removed features

These are the things you go looking for if you know the old SuperSocket. All of them were dropped on purpose, and there is no replacement API.

What was removedWhat to do instead
CollectSend / GetCollectSendData / CommitCollectSend, CollectSendIntervalMillSec Accumulate in your app and call SendCopied once
RawDataReceived / IRawDataProcessor<T> Handle it in the receive filter
IConnectionFilter Check in NewSessionConnected and Close the sessions you want to reject
Injecting ISocketServerFactory The library picks the implementation from SocketMode
AppSession.Items / PrevCommand / CurrentCommand, LogCommand Put fields on your own session subclass
The whole string-command protocol set (StringRequestInfo, TerminatorReceiveFilter, CountSpliterReceiveFilter, BeginEndMarkReceiveFilter, the non-generic AppServer/AppSession) Use a binary filter with AppServer<TSession, TRequestInfo>
The byte[]-based receive filter path (LeftBufferSize, toBeCopied, the offset/length arguments) Unified on ReadOnlySequence<byte>. MaxRequestLength is checked by the library against the unconsumed length
FixedHeaderSequenceReceiveFilter<T> Only the name changed. Use FixedHeaderReceiveFilter<T>

Setup also lost two arguments nobody used (socketServerFactory, connectionFilters), and the hook derived classes used to override was renamed to OnSetup.

11. Optimizations considered and rejected

These came up as candidates during the performance review (2026-08-14) and were rejected. They are easy to propose again, so the reasons are recorded here.

CandidateWhy it was rejected
Pooling (reusing) Session / AppSession / Pipe The biggest potential win, but the stability cost is exactly the counterweight. Fields on the app's derived AppSession subclass, filter instance state, and event subscriptions could leak between sessions — and that breaks a contract in app code the library cannot control.
PipeScheduler.Inline (running the reader inline) FlushAsync would end up running the app's request handler on the IOCP thread → risk of receive stalls and deadlocks. It conflicts with the design intent behind ReceiveInlineOnIocpThread, which draws the line at "inline only as far as advancing the pipe".
Replacing ChannelSendingQueue with a hand-rolled lock-free queue The queue is per session, so contention is nearly absent, and this is tens of nanoseconds against the microseconds of a send syscall. No gain to justify the risk of reimplementing EnqueueAsync (waiting, cancellation, completion semantics).
Making SessionID a value rather than a GUID string Two allocations per connection is a shame, but SessionID: string is a public contract and apps may depend on its format.
Changing the _sessionDict comparer from OrdinalIgnoreCase to Ordinal The gain is too small to justify the compatibility risk.
Coalescing send batches Scatter-gather (BufferList) already sends N segments in one syscall. Adding a copy would be a net loss.
Striping the shared hot-path counters It was actually implemented and measured: throughput dropped consistently by 1.2%, so it was withdrawn. At this load there is almost no cache-line contention, leaving only the cost of GetCurrentProcessorId.
Optimizing the UDP path The primary use is TCP and UDP has no LoadTest coverage. Held off, following the rule of not optimizing without measurement.
Kernel-level rewrites such as RIO / io_uring A large, platform-specific rewrite. It does not fit the character of a general-purpose .NET socket server.

How to remove the allocations that remain at the app boundary (receive filter, handler, send call site) is covered separately in Docs/GC_Copy_Minimization.md (Korean).
