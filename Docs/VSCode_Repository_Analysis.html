Whole-Repository Analysis in VS Code

How to get the VS Code C# language server to load the root unified solution SuperSocketLite2.slnx. That solution registers 33 C# projects, including the library, templates, tests, and tutorials.

1. Why this setting is needed

In standalone mode, the C# extension picks a default solution by searching for .sln files. This repository's unified solution is the root's .slnx, and several subdirectories each have their own .sln — so without pinning a default solution, the extension may not pick the unified one automatically.

If you open a C# file with no solution selected, Roslyn analyzes it inside a throwaway Canonical.csproj. That's fine for editing a single file, but it doesn't give you the repository's project relationships or its full set of source files.

2. Configuring the workspace

Create .vscode/settings.json at the repository root with this content.

{
  "dotnet.defaultSolution": "SuperSocketLite2.slnx"
}
.vscode/ is currently gitignored, so this setting has to be created locally on every machine that uses the repository. To analyze just the core library instead of the whole repository, use SuperSocketLite/SuperSocketLite.sln as the value instead.

3. Applying the setting

  1. Open the repository root as a workspace in VS Code (e.g. C:\github_dev\SuperSocketLite2).
  2. Make sure the workspace is trusted — in restricted mode, the C# extension runs in limited mode.
  3. Run Developer: Reload Window from the command palette.
  4. Wait for the solution and NuGet restore to finish, then try F12 again.

4. Confirming it loaded correctly

Switch the output channel to C# under View → Output and check the load message.

Log stateMeaning
Loads SuperSocketLite2.slnx and multiple projectsCorrect — whole-repository analysis is active.
Only Canonical.csproj loadsThe unified solution wasn't selected; only the files you've opened are being analyzed.
limited modeWorkspace trust wasn't granted.

5. When F12 only works for some symbols

SymptomLikely causeHow to check
Go-to-definition works within the same file but not across files The throwaway Canonical.csproj only knows about the files you've opened. Check the C# output log to see whether the real unified solution actually loaded.
Task, Socket, and similar work, but repository types fail The .NET reference assemblies loaded, but the repository's own projects didn't. Check dotnet.defaultSolution and whether you reloaded the window.
Go-to-definition only lands on an interface method's declaration F12 returns the statically-typed definition. Use VS Code's Go to Implementation to find the actual implementing candidates.

6. Verifying the solution's project list

Run this in a terminal to see which projects the unified solution includes.

dotnet sln SuperSocketLite2.slnx list
